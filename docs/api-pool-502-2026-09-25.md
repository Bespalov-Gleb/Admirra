# API pool: единичная 502 при опросе синхронизации, 25.09.2026

## Подтверждённые факты

- 12:20:33 UTC / 15:20:33 МСК: request_id `0b67f97af21ee86c4df6f98488c6264c`,
  GET `/api/integrations/sync/jobs/0a4e5731-7f32-47aa-8367-96a5bcab662f`,
  HTTP 502 за 1 ms, upstream **API1** (`127.0.0.1:8001`). Nginx:
  `upstream prematurely closed connection while reading response header from upstream`.
- Запросы этого же статуса за 5 s до и после — 200, порядка 10–20 ms.
  Соответствующего запроса/traceback в API нет; рестартов/OOM нет.
- Алерт Final5xx считает весь пул, а прежняя summary ошибочно называла только API2.
  В 12:33 UTC active alerts уже пусты: исходная ошибка вышла из 10-минутного окна.
- Runtime Uvicorn 0.52.4: idle keepalive 5 s. Nginx 1.24: upstream idle timeout
  не указан (default 60 s), cache 16 sockets. Опрос шёл каждые 5 s.

Вероятная причина — гонка повторного использования сокета при его закрытии API.
Это не доказательство точной причины прошлого TCP-разрыва: packet capture не было.
Изолированный тест подтверждает корректность нового срока хранения сокетов,
но не воспроизводит случайную production-гонку.

## Исправления

- Upstream `keepalive_timeout 3s`: Nginx первым освобождает простаивающий сокет.
  Время выполнения запросов не сокращено. Веса, health guards, маршруты, отсутствие
  глобального retry и политика платёжных/AI POST-запросов неизменны.
- Общий Vue poller больше не записывает FAILED при ошибке HTTP. Сохраняется последний
  подтверждённый статус; network/408/429/5xx повторяются с backoff до 15 s,
  максимум шесть последовательных ошибок для задания. Только GET, без повторного sync POST.
  Терминальные задания повторно не запрашиваются; запрос ограничен 10 s.
- Deadline — отдельный pending/timedOut результат, а не ложный success/failure.
  Все три вызывающих экрана показывают отдельное сообщение ожидания.
- Старый poller настроек интеграций заменён тем же механизмом с отменой при unmount.
  Фоновый опрос общего состояния не перекрывает сам себя; запрос ограничен 10 s.
- Dashboard pollSyncJobs уже сохранял предыдущий статус при HTTP-сбое и не
  синтезировал FAILED; его бизнес-логика не менялась.
- Исправлены только человеческие summary двух алертов; имена, severity,
  выражения и пороги сохранены, silences не добавлялись.

## Отдельный отказ Директа

Тот же SyncJob реально FAILED в 12:20:06, **за 27 s до 502**. Проект
«СТРОЙСФЕРА / ЯНД», background job `4c074d67-b92d-495b-9368-100b27254c3f`.
Воркер получил HTTP 200 на campaigns.get, затем IncompleteAdsSnapshot.
Старый лог сохранил только класс исключения, без кода ошибки провайдера/причины
валидации — точная первопричина не установлена. Повторный read-only запрос теми
же параметрами 25.09 вернул 4 кампании, без API error и без пагинации.
Нельзя утверждать, что это исправлено новым keepalive: внешнее обращение воркера
не идёт через ingress. Данные/coverage не подменялись, job не перезапускался,
fail-closed проверка полноты оставлена. Backend/worker релиз не требуется.

## Проверки и rollout

- 14 Node unit сценариев, 4 изолированных Chromium сценария настоящего Vue/Axios
  (502→успех, продолжительный отказ, реальный FAILED, deadline), всё внешнее IO заблокировано.
- 13 Python unit тестов Nginx/monitor/patcher. `git diff --check` чистый.
- Изолированный Nginx с loopback HTTP/1.1 backend idle=5 s: повтор через .25 s
  использует тот же upstream socket, через 4 s — новый. Все ответы 200,
  `proxy_next_upstream off`; production-конфиги/порты тест не использует.
- `ops.deploy_pool_keepalive`: точечный patch живого upstream (сохраняет 1:1 веса),
  snapshot, nginx -t и graceful reload. У Prometheus file bind mount сохраняется
  inode, выполняется promtool check + reload. При ошибке — rollback.
- Фронтенд собирать из clean git archive, не включать чужие dirty файлы.
  Overlay сохраняет landing/legal/старые chunks; API/DB/workers не перезапускать.
