# Этап 4: SQL-запросы сводки и метаданные интеграций

## Статус

Продолжение этапов 1–3. Код проверяется на втором сервере в изолированной
PostgreSQL с синтетическими данными, без внешних API и production-секретов.
Рабочее приложение, БД, nginx и расписания первого сервера не переключались.
Новая конфигурация двух серверов ещё не объявлена готовой к production.

## Что изменено

- `backend_api/summary_scope.py`: короткоживущий снимок только нужных настроек
  интеграций и балансов. Один SELECT с проекцией колонок; OAuth/API-токены и
  полные ORM-объекты не загружаются. Наличие активной кампании проверяется EXISTS.
- `StatsService.aggregate_summary`: текущий и прошлый периоды используют один
  набор настроек выбранных целей, VK-действий и интеграций. Метаданные выбранных
  кампаний читаются один раз вместо нескольких запросов на каждый период.
- «Данные целей ещё синхронизируются»: EXISTS вместо COUNT всех подходящих строк
  `metrika_goals`. Сам расчёт суммы лидов по-прежнему суммирует все нужные строки.
- Балансы берутся из уже загруженных метаданных; правило активных кампаний,
  исключение пустого/нулевого баланса, валюты и канальная разбивка сохранены.
- `folders.py`: общий набор метаданных на папку/ТОП-проекты загружается после
  определения доступных проектов и используется во всех канальных расчётах.
  Каждый дочерний расчёт сужает набор до своих client IDs; расширить снимок нельзя.
- Подробный штатный вывод идентификаторов/балансов при каждом расчёте перенесён
  с INFO на DEBUG, чтобы не создавать лишний объём журналов на горячем пути.

Это **не** Redis-кэш итоговых цифр и не глобальный/session-кэш. Снимок явно
передаётся между чистыми чтениями одного запроса, не сохраняется для следующего
запроса и не должен переиспользоваться после записи/commit. Авторизация остаётся
обязательной на каждом API-запросе. Получение самого снимка не даёт прав доступа.
Смена целей/баланса/активности видна следующему запросу без ожидания TTL.

## Проверки

`tests/test_summary_queries.py` использует PostgreSQL 15 из изолированного compose,
свежую схему на каждый тест, типы колонок и индексы статистических моделей.
Тестовых клиентов/кампании он создаёт самостоятельно; внешние сервисы не вызывает.

- Яндекс: 34 лида Метрики, не 65 native-конверсий Директа; точный override
  направления и отдельный override прошлого периода не потеряны.
- VK: в CPL входят только выбранные лидовые действия, не 999 трафиковых конверсий.
- Метрика/Авито и разные проекты с пересекающимися ID целей не смешиваются при
  повторном использовании метаданных строками папки.
- Исторические цифры архивной кампании остаются, её баланс больше не отображается.
- Изменение выбранных действий и баланса видно при следующем вызове.
- Сохранены legacy fallback выбранной цели на companion-интеграции Метрики и
  состояние «лиды не настроены» у VK с пустым выбором.
- ТОП-проекты читают метаданные один раз, только после определения доступных проектов.
- EXPLAIN ANALYZE на 10 001 подходящей строке: COUNT читает 10 001 строку,
  EXISTS останавливается после первой. Это синтетическая проверка формы запроса,
  не нагрузочный тест production.
- Дифференциальная матрица: 128 сочетаний проектов, каналов, кампаний и включённых/
  выключенных трендов. Полные ответы равны предыдущей реализации `c4d0412`;
  SELECT-запросов в матрице **1 494 → 868** (−41,9%).
- Смешанная сводка одного проекта без трендов: **15 SELECT**, настройки читаются
  один раз на четыре канальных/общих расчёта.
- Полный регрессионный прогон с исходниками: **282 passed, 1 skipped,
  1 deselected, 46 warnings**, 19,05 с. Пропущена опциональная дифференциальная
  проверка без монтирования предыдущего исходника; она проверяется отдельно.
  Deselected — старый тест Vue-файла, не входящего в backend-артефакт.

Отдельный дифференциальный запуск (из staging-каталога):

```sh
TEST_IMAGE=admirra-devops:c4d0412 docker compose -f ops/compose.isolated.yml run --rm \
  -e SUMMARY_BASELINE_FILE=/baseline.py \
  -v /opt/admirra-staging/release-c4d0412/backend_api/stats_service.py:/baseline.py:ro \
  tests --disable-warnings -s tests/test_summary_queries.py
```

## Важная находка по корректности — отдельная задача

Старая реализация `aggregate_summary(platform='avito')` повторно использует
`metrica_convs` как `yandex_convs_for_cpa` даже без статистики Яндекса. При
расходе Авито 500 и 3 лидах канальный `cpa` получается 83,33 вместо 166,67:
знаменатель равен 3 + 3. Это воспроизводится **и в baseline**, не внесено
оптимизацией. Составной CPL папки пересчитывается отдельно и в этом примере верен.

В данном performance-изменении формулы намеренно не менялись. Перед исправлением
нужно проверить потребителей канального `cpa`, трендов, CPL детектора/отчётов и
получить отдельную регрессионную матрицу. Не считать совпадение с baseline
доказательством корректности каждой исторически существующей формулы.

## Что остаётся для ускорения страницы

Эта работа сокращает SQL round trips, но ещё не устраняет все агрегаты N×проектов
и не объединяет четыре summary + три goals HTTP-запроса на карточку проекта.
Следующий шаг: пакетный endpoint/read model для карточек и ТОП-проектов с теми же
правами и правилами атрибуции; отмена устаревших запросов при смене фильтра;
корректная инвалидация кэша после commit. Нужен смешанный нагрузочный замер с
ночной/ручной синхронизацией, SSE и отчётами, а не только тесты одной сводки.

Меньше SQL-запросов не означает автоматические −42% времени загрузки страницы.
Скорость первого открытия зависит от тяжёлых суммирующих SQL, внешней Метрики,
числа HTTP-запросов и фронтенда. Переход на два сервера и очереди в первую очередь
изолирует пользовательские запросы от тяжёлых фоновых работ; фактический эффект
нужно измерить до и после безопасного cutover. Остальные gates этапа 3 остаются.

## Документация
