# T03/T07 — короткие транзакции goals-only Метрики

Подготовленный durable worker, не изменение включённой production-синхронизации. Общая ручная/ночная синхронизация пока не переведена на этот обработчик.

## Что сделано

`automation.metrika_goal_work.execute` заменяет goals-only ветку `automation.work_handlers`:

1. Короткая read session получает выбранные цели/счётчики, профиль, источник, исторические имена и окно. На выходе — обычный detached `GoalPlan`, без ORM-объектов и открытого соединения.
2. Сессия закрывается до создания API-клиента, ожидания очереди и всех HTTP-запросов. Собираются **все** счётчики; ошибка/невалидный ответ не превращаются в нули и не приводят к частичной записи.
3. Короткая write transaction блокирует проект и интеграцию, повторно проверяет настройки и атомарно заменяет окно с уведомлениями. Внешних запросов внутри этих блокировок нет.

Сверяются проект/владелец/статус, платформа и статус подключения, выбранные цели/счётчики/primary goal, токены, профиль/agency mode и UTM source. Секреты остаются только в памяти и исключены из `repr` плана; нет токенов в job payload/ошибках/документации.

Если настройки сменились во время HTTP, выбрасывается типизированная retryable `GoalSettingsChanged`: полученные строки отбрасываются, следующие попытки прочитают новые настройки. Изменившаяся авторизация/принадлежность не получают старый ответ. При следующем запуске paused/revoked/deleted проект пропускается без вызова провайдера.

Запуск требует контекста durable job fence. Проверка lease выполняется в **outer COMMIT**, а не на release savepoint. Просроченный/замещённый worker не может сохранить результат. Уже существующая эксклюзивность `resource=integration:<UUID>` разделяет goals-only и полный sync в новом runtime. Одновременный запуск legacy и durable writers не разрешён; legacy process-local lock не обеспечивает межхостовую защиту.

## Совместимость

- По-прежнему суммируются выбранные цели по выбранным счётчикам, без повторного накопления при retry.
- Avito использует только собственный Metrika grant/login/UTM-фильтр; нет fallback на токен Директа другого кабинета.
- `goal_window` — общий helper для legacy и durable: первая загрузка 90 календарных дней включительно; последующие — исходное окно с прежним `METRIKA_GOALS_LOOKBACK_DAYS` (default 30 дней назад, то есть 31 дата включительно). Неверный optional lookback по-прежнему игнорируется. Перевёрнутый диапазон явно отклоняется.
- Никаких новых DB-столбцов/миграций, изменения формулы лидов, обнуления истории, отправки отчётов или платных API-проверок.
- Это не единая монотонная revision всей системы: сравнивается точный snapshot полей перед записью. Общий settings-revision/cache invalidation и полный sync partial-status остаются в T04/T06/T07.

## Проверки

Первый targeted PostgreSQL suite goals-work + существующие goal-batch/full-sync/detector-isolation: **46 passed**, 21 warnings, 16,37 s. API заменён синтетическими ответами, SQL/транзакции/fencing настоящие. Проверки:

- ноль checked-out SQL connections в конструкторе API и в metadata/stat requests;
- сумма двух счётчиков, идемпотентный retry и прежнее окно;
- ошибка второго счётчика сохраняет прежние 34 лида;
- восемь изменений настроек во время HTTP запрещают запись;
- истёкший lease откатывает уже подготовленную замену;
- отдельный Avito token/login и escaping UTM, отказ без его grant;
- paused project без HTTP, запрет запуска без fence, секреты не попадают в repr.

Полный source-bind regression: **441 passed, 1 skipped, 1 deselected**, 47 warnings, 95,88 s. Прогон использует обновлённый test-only WAL budget; после проверки рабочий сайт отдельно ответил HTTPS 200 и остался на `cdf0a4d`, контейнеры production не перезапускались. Committed image acceptance — отдельная последующая запись.

## Ограничение изолированного стенда

Во время image acceptance предыдущего outbox-коммита PostgreSQL тестового стенда исчерпал 512 MiB tmpfs: `PANIC ... pg_wal ... No space left on device`. Прогон с ошибками не принят. Рабочая БД не затрагивалась. После перезапуска синтетического экземпляра запускается отдельная повторная проверка.

В `ops/compose.isolated.yml` установлены test-only `max_wal_size=128MB`, `min_wal_size=32MB`, `checkpoint_timeout=30s`, `checkpoint_completion_target=0.5`. Это контроль роста WAL между checkpoint при частом создании/удалении тестовых схем на tmpfs; более раннее завершение checkpoint ценой большей интенсивности IO здесь осознанно ограничено синтетическим стендом. max_wal_size — мягкий предел, не гарантия против любого заполнения диска; [PostgreSQL 15: WAL/checkpoints](https://www.postgresql.org/docs/15/runtime-config-wal.html). Production PostgreSQL параметры не менялись. Параллельные suites на одном Compose stack не использовать; независимым прогонам нужны разные test stack IDs.
