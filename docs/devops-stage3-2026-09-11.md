# AdMirra — защита отправок, общий read-cache и загрузка истории

Дата: 11 сентября 2026. Продолжение этапов 1–2.

## Статус и границы

Реализован следующий пакет кода для двух узлов. Он проверяется на изолированном
стенде сервера 2, **не включён на рабочем сайте**. Production PostgreSQL, nginx,
приложение, платежи, расписания и отправки клиентам этим этапом не изменялись.
Независимое backup-хранилище пользователь организует отдельно. Оно не единственное
оставшееся условие запуска: незакрытые инженерные задачи перечислены ниже.

Новые миграции идут строго после `dd4e5f6a7b8c`:

1. `ee5f6a7b8c9d` — журнал попыток отправки каждому получателю.
2. `ff6a7b8c9d0e` — долговечное состояние загрузки истории.

Prepared worker-compose теперь ожидает `ff6a7b8c9d0e`. Сам по себе файл compose
не применяет миграции и не является разрешением запускать старые и новые воркеры вместе.

## Отчёты: результат по каждому получателю

`report_route_attempts` хранит delivery UUID, SHA-256 маршрута получателя, канал,
состояние, номер попытки, fencing token и журнал ручных решений. Попытка фиксируется
в PostgreSQL **до** сетевой отправки. Один и тот же фактический Telegram/MAX/email
получатель в рамках одного ReportDelivery не получает повтор только из-за повторного
вызова обработчика. Разные ReportDelivery намеренно считаются разными отчётами.

Состояния:

| Состояние | Повтор |
|---|---|
| `accepted` | Провайдер подтвердил приём; повтор пропускается как успешный |
| `rejected` | Есть свидетельство отказа до приёма; повтор разрешён |
| `sending` | Попытка началась; параллельный отправитель её не повторяет |
| `uncertain` | Итог неизвестен; повтор запрещён до внешней сверки |

Это не обещание exactly-once доставки через стороннего провайдера и не доказательство,
что человек прочитал сообщение. В неоднозначном случае система выбирает ручную сверку,
а не риск повторной рассылки.

- Read/write timeout, 5xx, некорректный успешный ответ и потерянный DB commit не считаются
  доказательством неотправки. После такой ошибки PNG не подменяется второй отправкой PDF.
- После доказанного отказа PNG PDF fallback сохранён.
- Для SMTP различаются ошибка авторизации/явный отказ и обрыв после DATA. Результат
  сетевой операции переносится обратно из `asyncio.to_thread` — ContextVar сам этого не делает.
- Для MAX успешный статус должен содержать объект созданного сообщения, не произвольное 2xx.
- Прогресс email фиксируется после каждого адресата, а не после всего списка.
- Ошибка финального сохранения больше не стирает уже записанные результаты соседних маршрутов.
- Общий статус не становится `sent`, пока остаётся маршрут с неизвестным итогом.
- Устаревший прямой sender расписаний отключён при включённой защите; действующие ручная,
  тестовая и автоматическая отправки используют ReportDelivery pipeline.
- Миграция помечает старые sending/failed/partial отчёты без per-recipient доказательств.
  Они не считаются безопасными для слепого повтора. Первая попытка повтора создаёт
  `uncertain` маршрут без обращения к провайдеру.

### Сверка

В `delivery_results` возвращаются `route_states` и `requires_reconciliation`.
Ошибка получателя объясняет необходимость проверить получение перед повтором.

Добавлен авторизованный endpoint:

```text
POST /api/reports/deliveries/{delivery_id}/reconcile
{"route_key":"<64 hex из route_states>","decision":"accepted|retry","reason":"Результат внешней сверки"}
```

Доступ — только владельцу ReportDelivery. Решение не отправляет сообщение само:
`accepted` фиксирует подтверждённый приём, `retry` разрешает последующий обычный approve
этого маршрута. Нужна содержательная причина; actor/time/reason сохраняются. Пока batch
отправляется, сверка запрещена; для зависшего `sending` маршрута дополнительно выдерживается
15 минут. Старый token после решения больше не может изменить результат.

Отдельный диалог сверки в frontend **ещё не добавлен**. До него операции доступны через
owner-authenticated API; действующий интерфейс показывает текст ошибки. Нужен полноценный
UX проверки отдельных получателей до массового включения.

Диагностика `python -m ops.work_status` теперь сигнализирует и об unknown/зависших
получателях. Логи/JSON диагностики не выводят их адреса или тексты отчётов.

## Общий кэш чтения

`core/shared_read_cache.py`: отдельный Redis, JSON-only, ограниченный размер записи,
TTL и объединение одинаковых запросов из разных процессов через временную блокировку.
Потерявший блокировку loader не может перезаписать результат нового владельца.
Ошибка или отмена не заполняет кэш; lock имеет конечный срок жизни.

Первый реальный потребитель — YandexMetricaAPI:

- conversions-by-dimension: TTL 60 секунд;
- список целей счётчика: TTL 30 секунд;
- scope учитывает fingerprint credential, профиль, полный URL и параметры: даты,
  счётчик, выбранные цели, dimensions, фильтры и attribution;
- исходный token, логин и query не помещаются в Redis-ключи;
- HTTP-ошибки, некорректные/усечённые ответы не сохраняются как «0 лидов»;
- при смене token/profile/settings используется другой ключ;
- прежний process-local goal cache обходится в shared-режиме;
- при отказе cache Redis вызывается исходный loader; отдельный provider limiter
  продолжает ограничивать запросы. При долгом занятом lock возвращается ошибка ожидания,
  а не выдуманная пустая статистика.

Объединение GET-запросов — оптимизация, не бизнес-идемпотентность: eviction, истечение
lock или cache outage могут вызвать повторный внешний GET. TTL означает ограниченную
давность данных. Это **не кэш SQL-агрегатов всего дашборда** и не кэш авторизации.
Проверки доступа к проектам остаются перед сервисными вызовами. Мутирующий summary,
планы, платежи и отправки не обёрнуты в cache decorator.

Включение отдельным флагом:

```text
SHARED_READ_CACHE=true
READ_CACHE_REDIS_URL=<секретный URL отдельного cache Redis>
```

По умолчанию выключено. URL находится только в закрытом env, не в git. Не использовать
broker Redis как вытесняемый cache. Для full dashboard read-model ещё нужна транзакционная
инвалидация и проверка всех путей записи; старый неиспользуемый cache_response не включён.

## Загрузка истории «Динамики»

При `DURABLE_TASKS=true` API не создаёт daemon thread и не хранит прогресс в dict.
`history_backfill_runs` — текущее состояние отдельно для каждого проекта; периоды —
долговечные `history.backfill` jobs с outbox. Пересекающиеся запросы на группу проектов
дедуплицируются блокировкой Client, а не ключом комбинации проектов.

- История до 12 месяцев, окна до 90 дней. Только активные рекламные интеграции
  Direct/VK/Avito; отдельная Метрика-авторизация не создаёт бесполезный history job.
- Один исторический chunk одновременно во всей системе. Он использует тот же
  `integration:<id>` ресурс, что ручной/ночной/goals sync.
- Очередь `sync.backfill` обслуживается существующим nightly worker, дополнительный
  процесс и резерв RAM не добавлены. Manual/nightly имеют приоритет при claim.
- Publisher также приоритизирует manual/reports/maintenance/nightly перед историей,
  чтобы большой backfill не задерживал постановку новых ручных задач.
- Старые окна идут раньше новых. Между chunks сохраняется throttle (по умолчанию
  минимум 15 секунд, фактическая пауза может быть больше из-за republish/очереди).
- Сбой окна не маскируется под успешную загрузку всего периода: `partial`, число
  завершённых/ошибочных шагов и cooldown хранятся/восстанавливаются из PostgreSQL.
- Worker-crash recovery использует общие lease/fencing правила.
- Исторический режим не обновляет статус и timestamp обычного sync, не запускает
  детектор и LLM-гипотезы на каждом окне. Ошибка выбранных целей Метрики не замалчивается.
- При retention промежуточные успешные шаги активного прогона не удаляются. Итог
  сохраняется отдельно до удаления старых терминальных jobs.

Legacy path оставлен для текущего однопроцессного production. Перед переключением
нужно завершить **и старый in-memory backfill**, не только SyncJob.

## Проверки и артефакт

Тесты выполнялись на сервере 2: настоящий PostgreSQL 15.18 и Redis 7.4, internal
Docker-сеть без опубликованных портов и внешних API, non-root/read-only container.
Реальные клиенты/рассылки/платежи не использовались.

Проверены конкурентная отправка одного адресата, потеря DB после приёма провайдером,
crash до сохранения результата, неизвестный итог и запрет повтора, SMTP/thread evidence,
PNG fallback, ручная сверка и её ownership, миграции/FK/downgrade, общий кэш из восьми
независимых loops, смена scope/token/целей, ошибки и отмена loader, истёкший lock,
backfill race/rollback/приоритеты/resource locks/retention/cooldown и прежние regression tests.

Код сохранён локально: `737ea25` и дополнение `c4d0412` (историческая загрузка
не скрывает ошибки каталога/детализации Direct; проверены пустой и непустой пути).
Push и production deploy не выполнялись.

Готовый образ на сервере 2: `admirra-devops:c4d0412`.
Image ID: `sha256:6589648fd2d9ef4b58c8fc16f7094f702cab2f1b52bf91038fa2140137a374e3`.
Исходники из коммита: `/opt/admirra-staging/release-c4d0412/`.

**Image-only приёмка: 271 passed, 1 deselected, 46 warnings, 16,06 секунды.**
Bind mount с исходниками отсутствовал. Единственный deselected — Vue-тест: frontend
намеренно не включён в backend artifact. Это контрольный набор backend-тестов,
не весь репозиторный suite и не нагрузочная приёмка production.

Дополнительно: `pip check`, единственный Alembic head `ff6a7b8c9d0e`, OCI release label,
отсутствие `.env`, `.git`, uploads и приватных `.key` в образе; синтаксис prepared
worker-compose. Секреты и подключения production для этого не использовались.

После приёмки тестовые PostgreSQL/Redis и internal Docker-сеть остановлены/удалены.
Их данные были синтетическими в tmpfs; образы и исходные release artifacts сохранены.
Production проверен read-only: HEAD `cdf0a4d`, прежние контейнеры без перезапуска,
WireGuard active; публичный `https://admirra.ru` вернул HTTP 200.

## Оставшийся путь к production

1. Подготовить приватный DB-доступ, DB/Redis credentials и ACL, firewall, deploy-user,
   безопасную передачу env. Production Redis/воркеры ещё не включены.
2. Общие artifacts/uploads/public exports для API и workers на разных хостах;
   проверить in-memory public tokens, AI SSE и graceful drain. API-2 и nginx upstream
   ещё не включены.
3. Полные partial-status для обычного sync, короткие DB-транзакции, tenant fairness,
   SQL/N+1 оптимизация и read-model cache с инвалидацией после commit.
4. UI сверки отправок, дополнительное разбиение монолитных обработчиков reports/billing,
   независимая идемпотентность платных LLM-операций. Это не покрыто одним generic ledger.
5. Метрики и уведомления дежурному, смешанная нагрузочная приёмка, ночной прогон,
   failure/restore drill и проверенный rollback. До destructive migrations/cutover —
   независимый backup и проверенное восстановление.
