## 1. Цель и ограничения

### 1.1. Результат

Перевести проект с одного совмещённого API/фонового процесса на управляемую двухсерверную схему, сохранив существующие пользовательские возможности и корректность цифр. Должны быть обеспечены:

- изоляция интерактивных запросов от синхронизаций, рендера отчётов и фоновых AI-комментариев;
- безопасная доставка и восстановление задач, понятные частичные ошибки и свежесть данных;
- одинаковые файлы, ссылки, права и результаты независимо от API-реплики;
- измеримое уменьшение HTTP/SQL-запросов и задержек дашборда;
- общие квоты внешних API и защита от повторных учётных/платных операций;
- воспроизводимый деплой, мониторинг, независимый backup, проверенный restore и откат;
- возможность добавить worker/API-узлы без переписывания бизнес-процессов.

### 1.2. Не менять в рамках инфраструктурной работы

- Цены, включая оставленные пользователем тестовые цены, состав тарифов и политику White Label через заявку.
- Продуктовую доступность AI, лимиты и правила списаний без отдельного согласования. Исправление гонок не должно менять согласованную экономику.
- Атрибуцию лидов, НДС, формулы детектора и грейс-периода «для ускорения». Известные ошибки исправлять отдельными регрессионными изменениями.
- Расписания, часовые пояса, получателей отчётов и объём AI-prewarm без инвентаризации и явного решения.
- Дизайн лендинга/ассистента и пользовательские незакоммиченные правки, не связанные с этим ТЗ.

Не включать автоматически Kubernetes, шардирование, Redis Cluster, RabbitMQ, managed-сервисы или платное S3. Они не являются обязательным условием двухсерверного разделения.

### 1.3. Что нельзя обещать

Два узла с PostgreSQL и входным nginx на сервере 1 — не полноценный HA. Отказ сервера 1 останавливает основную БД и публичный вход. Redis на сервере 2 также одиночный. Балансировка API не устраняет эти точки отказа. RPO/RTO и скорость подтверждаются испытаниями, не количеством серверов или успешным unit-suite.

## 3. Целевая архитектура и обязательные инварианты

```text
Пользователь → HTTPS / nginx / frontend на сервере 1
                         ├─ API-1 на сервере 1
                         └─ API-2 на сервере 2, только через VPN
                                  │
API / workers / scheduler ──→ PostgreSQL на сервере 1
                             бизнес-данные + jobs/outbox + revisions + tokens
                                  │
Единственный scheduler + dispatcher → Redis broker на сервере 2 → workers
API / workers → Redis limiter на broker → внешние рекламные API
API / workers → отдельный Redis cache → безопасные результаты чтения
API / workers → общее файловое API на сервере 1 ИЛИ выбранный private object storage
БД + файлы + конфигурация → независимое шифрованное backup-хранилище
```

Инварианты для всех задач:

1. PostgreSQL — источник истины бизнес-операций и состояния задач; потеря Redis не удаляет уже принятые durable jobs.
2. Только одна сторона владеет выполнением одного ресурса/задачи; истёкший lease не даёт старому worker права на commit.
3. Модель доставки at-least-once; бизнес-идемпотентность строится отдельно. Не обещать exactly-once внешних отправок/LLM без поддержки провайдера.
4. API-реплики не запускают DDL или периодические business-jobs. Миграции — отдельный шаг, scheduler — отдельная роль.
5. Tenant/права проверяются сервером до чтения кэша, файла, job, диалога и перед чувствительным выполнением после ожидания в очереди.
6. Один объект/отчёт/ссылка доступен с обеих реплик. Sticky sessions не заменяют общее состояние.
7. Синхронизация не превращает сетевую ошибку или частичный ответ в нули. Пользователь видит полноту и свежесть.
8. Платежи, AI-баланс, права и разрешение повтора отчёта не опираются на вытесняемый кэш.
9. Отказ кэша — ограниченная деградация чтения; отказ limiter — остановка затронутых внешних запросов, не обход квот.
10. Для переключения есть проверенный совместимый rollback artifact; восстановление всей БД не является штатным откатом кода.

### 4.3. Ресурсные бюджеты — P0 перед совместным запуском

`ops/compose.workers.yml` — подготовленный шаблон, не окончательный capacity plan. Сумма его текущих memory limits близка к объёму RAM второго узла ещё без API-2 и ОС. Нельзя просто добавить API поверх всех сервисов с прежними лимитами.

Требования:

- Составить таблицу процессов, дочерних prefork, CPU/RSS/PSS, DB pools, Redis pools, временного диска и пиков рендера. Учитывать parent/control/heartbeat, не только business-children.
- На каждом узле оставить не менее 1,5 GiB стартового запаса для ОС/page cache/пиков; финальные ограничения проверить нагрузкой. Swap не считается рабочей RAM.
- Старт API — по одному процессу на узел. Увеличение до двух — только после пересчёта соединений/памяти и замера пользы.
- Стартовый общий sync cap — 4, tenant cap — 2, один writer на integration. История входит в эти 4, а не создаёт дополнительные слоты.
- Один тяжёлый renderer одновременно. AI-prewarm не должен отнимать резерв manual sync или интерактивного AI.
- Если RAM не хватает, уменьшить concurrency, объединить только совместимые лёгкие consumer-роли с сохранением приоритетов или временно оставить API-2 выключенным. Для полного закрытия двух-API этапа затем уменьшить пики/увеличить ресурсы и повторить испытания.
- Контролировать AOF rewrite RSS, `/tmp`, PDF/PNG Chromium и логи. Для каждого контейнера — ограниченные RAM/PIDs/CPU, rotation логов и stop grace.
- Держать ресурсный manifest рядом с release manifest; менять лимиты вместе с кодом/проверками, не вручную без журнала.

Формула соединений: `Σ(число процессов × (pool_size + overflow)) + отдельные heartbeat/control/migration/monitor connections`. Начальный ориентир суммарно до 70–80 подключений, но также обязательны реальные ограничения: `admirra_api` 30 на обе реплики вместе, `admirra_worker` 20 на все worker/control процессы вместе, HAProxy maxconn 80. Приближение к любому из них — gate failure. Не увеличивать все лимиты вместо устранения удержания соединений.

## 5. SEC — секреты, хосты и воспроизводимый релиз

### SEC-01. Доступ к серверам и секреты — P0

Реализация:

1. Проверить SSH host fingerprints независимым способом через провайдера/консоль. Не отключать host-key verification.
2. Создать отдельного deploy-пользователя и ключ, минимальные необходимые sudo-команды/службы. Доступ к Docker socket эквивалентен полномочиям администратора хоста; не называть членство в docker-группе ограниченным доступом.
3. Проверить вход новым ключом в отдельной сессии и наличие консоли восстановления. Только затем по согласованию отключать password/root login и ротировать ранее раскрытые root/API-пароли.
4. Провести inventory секретов по потребителям: PostgreSQL, Redis, JWT, encryption key рекламных токенов, площадки, AI, платежи, SMTP, Telegram/MAX. В manifest сохранять имена и fingerprints/версии, не значения.
5. JWT signing key и ключ расшифровки рекламных токенов должны быть совместимыми на обоих API/нужных workers. Случайная новая генерация недопустима. Для ротации encryption key нужен dual-read/миграция шифротекстов и отдельный rollback.
6. Ограничить env/state до 0600, родительские каталоги 0700; mounted ACL могут быть читаемыми процессом, но содержат хэши и лежат в закрытом каталоге хоста.
7. Runtime получает только нужные секреты. Scheduler не получает все платёжные/AI/почтовые ключи только из-за общего worker env; по мере разделения обработчиков сузить наборы.
8. Убрать секреты из stdout, HTTP ошибок, access logs, argv, CI artifacts, `docker compose config` outputs. Для поддержки — sanitization и request ID.

Приёмка: новый вход проверен, rollback доступа описан; negative-тесты runtime DDL/admin Redis проходят; secret scanning чистого артефакта и логов не обнаруживает значений; приложения читают существующие тестовые токены после обновления.

### SEC-02. Firewall и публичные порты — P0

- На сервере 1 оставить внешний ingress 80/443 и согласованный SSH/WireGuard. Backend/frontend bind loopback либо сеть, недоступная извне. Админку не открыть случайно.
- API-2 публиковать только на VPN-адресе/доверенной внутренней сети; доступ от server1 ingress. БД/Redis не публиковать в Интернет ни по IPv4, ни по IPv6.
- Сохранить действующие узкие private chains, проверить взаимодействие с Docker DNAT/FORWARD, рестартом Docker и загрузкой ОС. Добавлять правила без глобального flush; предусмотреть timed rollback для сетевых изменений.
- Проверить все реальные домены/aliases, webhook/OAuth маршруты и потребителей прямых портов до закрытия. Выдать отдельный список «оставлен открытым / почему».
- Метрики, control endpoints, диагностика и artifact write API — только приватный/авторизованный доступ.

Техническая основа Docker-фильтрации: проверять не только INPUT/UFW, но и путь опубликованного контейнерного трафика через Docker chains. [Официальная документация Docker](https://docs.docker.com/engine/network/firewall-iptables/).

Приёмка: внешняя проверка обоих IP/IPv6, 80/443/SSH работают по политике, private ports недоступны; проверены reboot и Docker restart в согласованном окне, новые соединения внутри VPN восстанавливаются.

### SEC-03. Build/release/CI — P1, чистый rollback — P0

- Один immutable backend artifact на API, workers и scheduler с разными entrypoints. Frontend — отдельный связанный artifact, если меняется контракт/UX.
- Использовать `ops/package_backend.py`, закреплённые requirements/base digests. CI build не должен зависеть от грязного рабочего каталога.
- Проверки: unit/integration, image-only suite, `pip check`, dependency/image/secret scan, миграционный head, список файлов, startup нужных ролей, SBOM или полный dependency manifest.
- Добавить CI pipeline и deployment lock. Registry — частный при наличии, либо проверенная доставка image archive с SHA-256; публичный registry не обязателен.
- Запрет `latest` как идентификатора релиза. Manifest содержит commit, image digest, schema head, config version, миграционный план, tests/evidence и rollback artifacts.
- Старый рабочий образ из исходного аудита содержит чувствительные материалы. Не публиковать его и не считать безопасным универсальным rollback. Собрать чистый совместимый rollback из контролируемого baseline, проверить запуск и чтение расширенной схемы.
- Сохранить минимум текущий и предыдущий проверенные релизы. Удаление старых чувствительных слоёв/кэшей — после безопасного отката и согласования, без volumes и действующих artifacts.

Приёмка: сборка из чистого checkout воспроизводимо проходит; на каждой роли совпадают release/digest; случайные frontend/probe/secret файлы не попали в backend; деплой двумя операторами не выполняется параллельно.

## 6. FILE — общие файлы, отчёты и публичные ссылки

Приоритет: P0 перед балансировкой API, P1 для полной приёмки.

### FILE-01. Выбор реализации без обязательного S3

Базовый вариант на уже арендованных машинах: отдельное приватное файловое API на сервере 1 с единым постоянным каталогом, например `/srv/admirra/artifacts`. Оба API и workers обращаются к нему через единый storage adapter. Это новая реализация, а не существующий сервис. Она сохраняет SPOF сервера 1, что фиксируется в runbook.

Если владелец предоставляет подходящее private object storage, реализовать тот же adapter поверх него. Не разворачивать собственный S3-кластер только ради названия; не считать два локальных каталога с периодическим rsync общим согласованным хранилищем. Offsite backup может быть S3, SFTP или иным подходящим хранилищем — отдельно от runtime storage.

Контракт adapter: `put`, `stat`, `open/read`, `delete`, при необходимости bounded multipart/streaming. Object key генерирует сервер; клиент не передаёт произвольный путь/URL. Метаданные в PostgreSQL: UUID, owner/tenant/scope, storage backend/key, mime, byte length, SHA-256, state, created/expires, version/revision.

Для приватного файлового API: VPN + аутентификация сервисных ролей, предпочтительно mTLS либо подписанные краткоживущие запросы с ограничением повторов; read/write/delete права разделить. Docker IP и possession object key не являются достаточной авторизацией. Файл не должен считываться по произвольному пути, symlink или внешнему URL. Ограничить размер/время upload, MIME, streaming memory, concurrent writes и временный диск.

### FILE-02. Атомарная запись и lifecycle

1. Зарезервировать metadata/state `uploading` в БД (название новое, схема проектируется).
2. Записать во временный объект/путь, вычислить hash/size, завершить атомарную публикацию объекта. Для filesystem — rename в пределах одного FS и требуемая durability; для object storage — завершение upload.
3. Коротким commit пометить объект `ready`; только после этого выдавать ссылку или включать его в отправку.
4. Crash между шагами не публикует битый файл. GC находит orphan/temp объекты после безопасного интервала, не удаляет referenced `ready` artifacts.
5. Очистка учитывает TTL, активные доставки, pending approval/reconciliation, backups и договорённую retention. Soft delete/tombstone и повторяемая cleanup job предпочтительнее безусловного удаления.
6. Snapshot отчёта неизменяемый: переотправка использует прежний artifact/revision, а не незаметно новый расчёт. Перегенерация создаёт новую версию с явной связью.

### FILE-03. Токены и legacy-ссылки

Сейчас `backend_api/reports/export_service.py` использует `_report_file_cache` / `_report_view_cache` и tempfile. Перенести публичные view/file tokens в PostgreSQL. Уже существующий DB-backed public PDF delivery-путь сохранить и привести к общему storage, не ломать его контракт.

Требования к публичной ссылке:

- криптографически случайный bearer token достаточной энтропии, в БД — hash, срок, scope/artifact, revocation, создатель;
- ограниченный TTL, `Cache-Control` по политике приватности, `Referrer-Policy: no-referrer`, отсутствие токена в аналитике/access logs;
- истёкшая/отозванная/несуществующая ссылка возвращает согласованный 404/410 без metadata leakage;
- нельзя заменить artifact_id/project_id и получить другой файл; недоступный storage не превращается в «ссылка не существует»;
- долгоживущие credentials не помещаются в URL; signed URL при object storage имеет короткий срок;
- загрузка аватаров и статических публичных изображений сохраняет существующую политику доступа, а приватные документы не становятся публичными по аналогии.

Для старых in-memory ссылок выбрать проверяемую стратегию: экспортировать состояние через закрытый одноразовый инструмент до остановки процесса либо удержать старый route до максимального legacy TTL и предложить переиздание. Если процесс уже потерял словарь, восстановление такого token не обещать. Не переключать старые URL случайным round-robin до завершения совместимости.

### FILE-04. Миграция файлов и приёмка

- Инвентаризация: uploads/аватары, report PDF/PNG/DOCX, report views, экспортные временные файлы, rejected leads и другие пути записи. Карта «producer → storage → consumer → retention → backup» обязательна.
- Переносить copy → checksum/size verification → metadata → чтение через adapter; старую копию удалять позднее отдельным шагом.
- Согласовать консистентность file snapshot и DB backup: восстановленная БД не должна ссылаться на отсутствующий объект. Immutable files + retention/tombstones должны покрывать PITR-окно.
- Тест: создать на API-1, прочитать на API-2, перезапустить API-1, повторить; worker записывает — оба API читают; отозвать — оба отказывают.
- Дополнительно: crash при upload, недоступный storage, full disk, checksum mismatch, oversized file, path traversal/symlink, чужой tenant, истечение TTL, range/download при необходимости, очистка без удаления pending отчётов.

Ориентиры кода: `backend_api/reports/export_service.py`, `backend_api/reports/router.py`, `backend_api/reports/scheduler.py`, все uses `UPLOADS_DIR`/`REJECTED_LEADS_DIR`. Новые adapter/migrations/операционные конфиги должны быть перечислены в release evidence.

## 7. DB — подключения, транзакции и обслуживание PostgreSQL

### DB-01. Runtime и миграции — P0

- Подключить новые роли только после проверки нужных DML/sequence/function прав на всех маршрутах. Не выдавать DDL для обхода ошибки startup.
- Отдельная migration identity, доступная только release job. Не передавать её API/worker.

Для каждого релиза выбрать maintenance/drain либо явный узкий список совместимых схем с тестами. Не отключать проверку схемы полностью.

### DB-02. Короткие транзакции и event loop — P1

- Инвентаризировать Session lifetime в sync, отчётах, Sheets, AI, billing и аналитике. Не держать транзакцию/соединение во время долгого внешнего HTTP/рендера/ожидания очереди.

- Настроить connect/pool/statement/lock/idle-in-transaction timeouts по типам работы. Сейчас prepared statement 60 s, lock 10 s, role idle-in-transaction 300 s; это потолки, не допустимая длительность каждого web-запроса.

Session не является объектом для совместного конкурентного использования; выбор threadpool/async должен сохранять изоляцию транзакций. [SQLAlchemy Session Basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html).

### DB-03. SQL/индексы/maintenance — P1

- Собрать свежие дельты `pg_stat_statements`, slow queries, locks, transaction age, rows/loops и планы на репрезентативном стенде. Не использовать месячную накопленную статистику как текущий RPS.
- Оптимизировать крупные повторяющиеся SELECT/upsert по keywords/groups/goals, scopes папок/сводки и campaign stats; не создавать индекс «на каждый фильтр».

- Определить retention технических логов/jobs/cache metadata; не удалять неопределённые доставки, бизнес-ledger и evidence списаний вместе с обычными логами.
- PgBouncer — условная подзадача: внедрять только при подтверждённой пользе. Transaction pooling требует проверки advisory/session state/prepared statements и direct migration path; не является лечением длинных транзакций.

Обоснование обслуживания: [PostgreSQL vacuum](https://www.postgresql.org/docs/15/routine-vacuuming.html). Ограничения pooler: [PgBouncer features](https://www.pgbouncer.org/features.html).

Приёмка DB: роли не превышают budget; нет Session leak после нагрузки/SSE cancel; API не блокируется внешним ожиданием внутри SQL-транзакции; миграции и совместимый rollback проходят на восстановленной копии; права/числа не меняются от смены процесса.

## 9. PERF — карточки, сводка и корректный кэш агрегатов

### PERF-01. Пакетный read API — P1

Сейчас сохраняется модель нескольких summary/goals HTTP-запросов на каждый scope. Реализовать versioned batch/read-model endpoint, например **новый** `POST /api/dashboard/cards/query`; допустимо согласовать другое имя. POST здесь только форма передачи фильтров, обработчик не выполняет внешнюю отправку/списание.

Вход: не более 20 видимых scopes, тип project/folder, IDs, текущий/сравниваемый период, channel, direction/campaign/goal/action filters, VAT/display mode, cursor при необходимости. Верхние границы дат/ID/размера запроса валидировать, общую сводку не превращать в неограниченный перебор всех клиентов.

Выход на scope: итоговые KPI, channel rows с CPL/дельтой в рублях, нужные totals, freshness/revisions/coverage, явная ошибка scope без внутренних деталей. TOP-5 — по согласованному CPL лучших, без лидов не показывать как лучший бесплатный результат; стабильная сортировка при равенстве и совместимость текущего UX.

Требования:

- Один batch authorizes все scopes; чужие IDs не возвращают данные/названия. Политика 403 всего запроса либо обезличенный per-scope error фиксируется контрактом и тестами.
- Не реализовывать batch как цикл старых 7 запросов на каждый проект. Метаданные/разрешения загружаются пакетно; stats SQL группируется по набору проектов/каналов и двум периодам.
- Для папки/сводки агрегация по всем разрешённым проектам выполняется в БД; пагинация не обрезает totals. ТОП ранжируется по согласованному полному scope.
- Общие вычислительные функции не делают commit/visit writes. Учёт посещения/snapshot detector вынести отдельным явным действием; cache hit не отменяет необходимый учёт визита, prefetch не имитирует визит.
- Детализацию целей догружать при раскрытии; не скачивать скрытые таблицы сразу. Изменение схемы — additive, старые endpoints сохранять на переходный период.
- Request-scoped metadata snapshot из этапа 4 не переиспользовать между пользователями/запросами или после записи.

Приёмочные бюджеты для проектируемого пути: ≤2 data HTTP-запросов на первые 20 видимых карточек без раскрытых деталей; ≤30 SQL-запросов на cold batch этих карточек, с ростом от 1 к 20 не более 10 дополнительных round trips. Это целевые ограничения, не утверждение о текущих цифрах; более строгий достигнутый бюджет сохранить regression-тестом. Внешние вызовы учитывать отдельно и не маскировать SQL-budget ускорением за счёт сотен HTTP.

### PERF-02. Frontend request lifecycle — P1

- Обновить живые Project/GeneralStats3/folder/summary consumers, сохранив мобильную верстку и согласованные подписи.
- При смене фильтра/проекта/периода применять AbortController, generation ID и обработку отмены без error-toast. Старый ответ не перезаписывает новый.
- Debounce только для ввода, не откладывать явный выбор; lazy-load скрытых деталей; одинаковые запросы не отправлять повторно несколькими компонентами.
- Скелетоны до первой загрузки, stale/partial state — отличимы от «нет данных». После sync/settings mutation обновляется нужный scope, не вся страница цепочкой независимых запросов.
- Проверить 10/20/100 карточек, быстрые переключения, медленную сеть, мобильные брейкпоинты, отсутствие бесконечных refetch loops.

### PERF-03. Aggregate cache и инвалидация — P0 перед включением кэша

Расширять безопасный механизм `core/shared_read_cache.py` либо создать отдельный adapter с теми же гарантиями. Не включать старый `cache_response`, исключающий пользователя из ключа, на tenant-data.

Ключ: namespace/version + tenant/owner + scope/access revision + project/folder IDs + канонические даты/previous period + platform + direction/campaign IDs + selected goals/actions + attribution + VAT semantics + algorithm version + settings/data revision. Массивы ID сортировать; сырые credentials, имена клиентов и запросы пользователя не помещать в ключи.

Рекомендуемый базовый механизм: durable revision в PostgreSQL увеличивается **в одной транзакции с изменением данных/настроек**; cache key включает revision. Post-commit outbox может прогревать/ускорять уведомление, но не является единственным источником инвалидации. Для membership/folder/global totals нужны соответствующие scope/tenant revisions. Авторизация выполняется заново по авторитетным данным; stale rights нельзя компенсировать TTL.

Гонки:

- Compute фиксирует revision и согласованный snapshot; перед публикацией проверяет, что не маркирует старые данные новой revision.
- Старый loader публикует только старый versioned key либо отбрасывается; после потери lock не перезаписывает новый результат.
- Redis flush/eviction не обнуляет DB revision и не «оживляет» старое значение. Rollback DB-транзакции не публикует новые данные/инвалидацию как состоявшуюся.
- После успешного mutation API возвращает новую revision; последующее чтение не отдаёт более старую как актуальную.

Обязательные invalidators: полный/частичный успешный commit sync, цели/действия/счётчики, campaign/direction mapping, план и его revision, detector settings, VAT-параметры, перенос/удаление/пауза проекта, team-права, интеграция/reconnect/token rotation, изменение папки и состава общей сводки.

TTL стартово 30–120 s для агрегатов с revisions, справочники по подтверждённой свежести; TTL jitter, bounded entry size, ограниченный single-flight. Это не разрешение ждать TTL после изменения плана. Cache outage: bounded concurrency DB fallback, короткий timeout/circuit breaker, отсутствие cache stampede. Ошибки источников не кэшируются как нули; partial result допускается только с явным статусом и соответствующим versioned contract.

Новые aggregate keys по возможности размещать внутри существующего `admirra:read:v1:*` с версией подпространства. Если нужны новые namespaces/команды — отдельная проверка ACL и согласованное обновление users, не `+@all ~*`. Кэш не хранит единственную копию payment/AI/run/delivery coordination.

Приёмка: cross-tenant negative tests, revoke rights, move folder, plan update, sync commit/rollback, loader race, eviction/outage/restart, cold/warm concurrency. Числа совпадают с DATA-contract; cache hit ratio, hit/miss latency и freshness записаны в evidence.

## 10. SYNC — ручная, ночная и историческая синхронизация

### SYNC-01. Инвентаризация и единый путь — P0

Охватить все инициаторы: кнопка «Синхронизировать», подключение кабинета/новые настройки целей, nightly producer, Dynamics backfill, legacy API routes, пользовательские повторные попытки. Построить карту `route/tick → dedupe key → integration resource → handler → commit → detector/cache/report`.

Сохранить действующий контракт `sync_jobs` для UI; новый `background_jobs` является execution ledger, а не заменой всех пользовательских статусов одним флагом. Не должно оставаться прямого тяжёлого sync внутри API или обходного daemon thread в durable-режиме.

Приём запроса должен быть durable: транзакция создаёт business job + outbox или присоединяет к существующему. Ответ 202 содержит job ID/status URL только после успешного commit. Потерянный publish восстанавливается dispatcher. Если запрос не сохранён, вернуть честную ошибку/Retry-After, не «запущено».

Совпадающие manual/nightly запросы для integration дедуплицировать по согласованному диапазону и настройкам. Более широкий новый диапазон нельзя потерять, просто вернув узкую running job: хранить follow-up/объединённое требование и показывать связь. Повтор запроса после сетевого обрыва не создаёт вторую независимую работу.

### SYNC-02. Частичные ошибки и полнота — P0

Спроектировать и сохранить per-stage outcome: источник/этап, диапазон, required/optional, coverage, fetched/validated/committed, время, retryability, sanitized error code. Требуется явная семантика верхнего статуса, например:

| Ситуация | Бизнес-результат | Данные/повтор |
| --- | --- | --- |
| Все обязательные этапы завершены | success | Watermark обновляется по подтверждённым диапазонам |
| Часть обязательных источников не обновилась | partial | Старые данные не стираются; повтор только затронутого участка |
| Ни один обязательный этап не выполнен | failed | Нет фиктивного обновления свежести |
| Доступ/токен отозван | action_required / существующий эквивалент | Не бесконечный retry; предложить переподключить |
| Корректный пустой ответ | success с 0 фактов | Пустота подтверждена ответом/coverage |
| Усечённый ответ/ошибка разбора/429/timeout | Не успешные нули | Сохранить прежние факты, retry по правилам |

Эти названия — семантический контракт, а не утверждение о наличии enum в текущей БД. Если нужен новый enum/state, сделать additive migration и frontend mapping. `background_jobs` сейчас имеет queued/running/succeeded/failed/uncertain; бизнес-полноту sync хранить отдельно, не менять transport-state бессистемно.

Watermark хранить отдельно по источнику/диапазону/набору целей или иной достаточной размерности. Один общий `last_sync_at` недостаточен для доказательства, что все каналы и весь отчётный период обновились. Изменение настроек во время fetch должно приводить к перепроверке revision, а не commit статистики от прежних целей как новой.

UI: «Часть данных обновлена», «Нет доступа», последняя успешная загрузка/ожидающий участок; ошибки без токенов. Reports/AI/detector получают coverage/freshness, не делают категоричные выводы на неполных данных без соответствующей политики.

### SYNC-03. Запись, lease и отмена — P0

- Сохранить пакетную запись Метрики; распространить fetch → validation/staging → короткий атомарный commit на оставшиеся источники и details/keywords/groups.
- Для каждого commit проверять актуальный fencing token/resource ownership. Истечение lease или потеря heartbeat запрещает старому worker продолжать записи. Проверка только в начале задачи недостаточна.
- Unique business keys фактов должны выдерживать duplicate delivery и crash после commit до ACK. Не очищать диапазон, пока новые данные не получены и не проверены.
- Исторические чанки bounded по времени/объёму; прогресс восстанавливается после рестарта. Detector/платный comment не запускаются после каждого historical chunk. Сохранить `test_sync_detector_isolation.py` и backfill regression.
- После commit увеличить нужные revisions и отдельно поставить downstream work. Сбой detector/комментария не откатывает уже корректно сохранённую статистику и не маркирует весь источник как не загруженный.
- Отмена/пауза/удаление integration во время очереди/работы: проверить доступное состояние перед fetch/commit, корректно завершить job; внешнее платное действие после отмены не повторять автоматически.

### SYNC-04. Квоты и справедливость — P1

Существующий общий limiter в `automation/provider_transport.py` должен охватывать все релевантные consumers, включая assistant tools/прямые клиенты, если используют ту же квоту. Проверить реальную размерность ограничений каждого провайдера: token, account, agency profile, counter, operation; текущие default RPS не являются официальной квотой.

## 12. REPORT — рендер, свежесть, доставка и ручная сверка

### REPORT-01. Единый pipeline — P0

Все manual/test/scheduled/weekly/monthly routes используют одну бизнес-модель:

```text
request/schedule occurrence
 → authorization + dedupe + required data coverage
 → waiting_data / pending approval
 → immutable snapshot + revision
 → render artifact once
 → delivery per recipient/channel
 → accepted / rejected / uncertain + aggregate result
```

Названия промежуточных статусов проектируемые; сохранить совместимость существующих `ReportDelivery.status` и route states. Не путать «провайдер принял» с «получатель прочитал». Для email SMTP acceptance не доказывает попадание во входящие.

Требования:

- Reports не строятся заново из live данных при retry одного получателя. Snapshot, period, goal scope, VAT, plan reference, comment version фиксируются.
- Approval/блокировки детектора, лимиты тарифа, пауза проекта и получатели проверяются по действующей продуктовой логике. Оптимизация не обходит обязательное согласование отчёта.

- Heavy PDF/PNG не задерживает notifications/sync, а скачивание не держит весь файл в памяти нескольких процессов.
- Переработать прямые export endpoints так, чтобы тяжёлый режим мог возвращать 202/status/download; сохранить совместимость клиента или выпустить вместе обновлённый frontend.

### REPORT-02. Barrier свежести — P1

Для отчёта сохранять требуемые integrations/metrics/date coverage и deadline ожидания. Готовность определяется успешным watermark источников, а не временем запуска cron и не статусом чужого общего batch.

### REPORT-03. Per-recipient ledger и UI — P0 для массовой отправки

Сохранить реализованный `backend_api/reports/route_ledger.py` и states:

### AI-02. Durable run и деньги — P0

Спроектировать `run_id` / idempotency contract (новая реализация, если отсутствует):

- Client request ID уникален в tenant/user scope; canonical request hash исключает использование того же ID с другим текстом/моделью. Повтор с тем же payload возвращает существующий run; с другим — конфликт.
- До внешнего вызова короткая транзакция проверяет право/тариф/concurrency и создаёт run с reservation по действующей экономике. Недостаточный баланс не проверяется двумя независимыми read-then-write.
- Состояния минимум различают queued/running/succeeded/failed/interrupted/uncertain usage; final billing operation имеет уникальный business key. Не обязательно менять публичные слова UI на технические enum.
- Usage фиксируется отдельно от результата текста, с provider request ID, token units/cost inputs и версией расчёта. Повтор webhook/ответа/worker не списывает повторно.
- Ошибка до обращения к провайдеру освобождает reservation. Неизвестный usage после обрыва не считать автоматически нулевой стоимостью и не генерировать второй запрос для «проверки».
- Reservation/settlement/refund и локальное списание должны быть идемпотентны; случаи невозможной provider reconciliation помечать и разбирать по согласованной политике.
- Перегенерация комментария — новая явно оплачиваемая/учитываемая операция согласно продукту, а transport retry — не новая генерация.
- Права/тариф/баланс не кэшировать с eventual consistency. После ожидания в очереди проверять доступ к scope и допустимость исполнения.

Миграции и операции ledger делать additive; не пересчитывать прошлые платежи и тестовые цены массово. Ротация AI-ключей и платные smoke-tests требуют отдельного защищённого доступа и лимита бюджета.

### AI-03. SSE, concurrency, инструменты — P1

- На `POST /api/assistant/chat` сохранить потоковую отдачу и heartbeat; текущий heartbeat около 12 s. События имеют явное завершение/ошибку/run ID. Sanitized error вместо вывода provider exception со скрытыми headers/URL.

- SSE: `proxy_buffering off`, исключить proxy/cache/compression buffering где оно мешает, сохранить content type и потоковые bytes; проверять все промежуточные nginx. Read timeout должен превышать heartbeat gap с запасом, но отдельный max run deadline ограничивает общую длительность.
- Для HTTP/1.1 upstream настроить keepalive/headers корректно; не включать WebSocket Upgrade для SSE по привычке. Сохранить Authorization, cookies, CORS/CSRF политику и реальный client IP только от доверенного proxy.
- Forwarded headers доверять известным ingress адресам, не всем клиентам. TLS/redirect/cookie domain/OAuth callbacks/payment webhooks должны работать через общий домен.
- Стабильные security headers/limits для uploads и API; публичные diagnostics не раскрывают структуру конфигурации.
- Логи содержат request ID, upstream, release, duration, status без токенов URL/Authorization/body. Заголовок release для QA допускается без внутренних секретов.

Семантика buffering/timeouts/retry: [nginx proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html). Выбор upstream algorithm и ограничения health: [nginx load balancing](https://nginx.org/en/docs/http/load_balancing.html).

### LB-03. Межрепличная приёмка

1. Авторизоваться через API-1, запросить проекты/диалог через API-2; refresh/logout/revoke проверяются на обеих.
2. Создать link/job/файл/run через одну реплику, получить статус/результат через другую и после restart первой.
3. Сменить план/цели/права на одной — другая не отдаёт старое как новое, не раскрывает чужой scope.
4. Поддержать длинный SSE, одновременно запросить дашборд; нет задержки heartbeat из-за sync SQL.
5. Исключить API-2, дождаться drain; API-1 продолжает работу. При kill API активный stream завершается понятным interrupted, без автоматического повторного списания.
6. Отключить VPN на стенде: API-2 исключается, server1 API сохраняет доступную функциональность; внешние tools/фоновые tasks корректно деградируют из-за server2 Redis.
7. Проверить все рабочие домены, callback/webhook/admin/landing/static routes, mobile frontend и CORS. Нельзя ограничиваться GET `/`.

## 15. OBS — метрики, алерты и операционная панель

Приоритет P1, минимальный мониторинг обязателен до canary.

### OBS-01. Минимальный стек

Использовать один небольшой Prometheus-compatible collector/store и dashboard/alerting либо уже имеющуюся у владельца систему. Выбор инструмента вторичен; не запускать тяжёлый logging stack без RAM/disk бюджета. Экспортеры/метрики приватные и без tenant/секретов в labels. Для полного падения обоих серверов нужен внешний heartbeat/uptime receiver: монитор только на этих машинах не может надёжно сообщить о собственном исчезновении.

Собрать:

| Область | Метрики |
| --- | --- |
| API | requests/status/duration p50/p95/p99 по route template, inflight, event-loop lag, threadpool wait, pool wait, active SSE, release/drain |
| DB | connections по role/state, long transactions, locks/deadlocks, slow/query-count budgets, size, vacuum/analyze, disk/WAL/archive lag |
| Jobs | queued/running/failed/uncertain, oldest ready age по queue, runtime/retry, outbox lag, stale lease, recovery/duplicate suppression, scheduler heartbeat/cursor lag |
| Sync | last success, coverage/freshness, partial/error type по provider, nightly batch duration, manual wait, provider 429/latency/quota wait |
| Reports | waiting_data/approval, render time/failure, accepted/rejected/uncertain routes, reconciliation age, storage errors |
| AI/billing | concurrent runs, time to first event/token, duration/cancel/loop budget, usage/settlement mismatch, idempotency conflict, webhook lag |
| Redis | memory/maxmemory, evictions отдельно cache/broker, AOF status/rewrite, rejected writes/ACL errors, command latency, connections, cache hit/miss |
| Hosts/files | CPU/RAM/swap/OOM, filesystem/inodes/free space, container restarts, WireGuard handshake, cert expiry, temp/artifact growth |
| Backups | last successful backup, WAL archive age, last successful restore drill, backup errors/size, offsite reachability |

Не использовать user_id/project_id/request_id как неограниченные Prometheus labels. Tenant-разбор — контролируемые structured logs/DB диагностика с доступом и retention. Логи не содержат bodies промптов, рекламные токены, адреса получателей или платёжные payload без специальной защищённой необходимости.

### OBS-02. Начальные пороги и обработка

Пороги ниже — стартовая политика для настройки, проверяется под нагрузкой и записывается в финальный operational manifest.

- Критично: DB недоступна >30 s, оба API unready >30 s, broker AOF/write failure, признаки повреждения/утраты принятого job, повторное учётное списание/tenant leakage — немедленный stop rollout.
- Scheduler heartbeat/cursor lag >2 min; oldest ready manual >30 s при доступной квоте; nightly не укладывается в согласованное окно; report uncertain требует действия, не бесконечного auto retry.
- Disk <20% warning, <10% critical; inodes аналогично; memory >85% устойчиво либо OOM — пересмотр concurrency. Redis broker >75% warning / >90% critical, broker evictions должны быть 0.
- p95/error-rate нарушает SLO 10 min либо canary хуже baseline по §18 — остановка расширения. 429 из-за собственной квоты отделять от provider outage.
- Backup старше 26 h при ежедневном расписании; WAL archive lag >5 min warning и >15 min critical при целевом RPO 15 min; restore drill просрочен по политике.
- TLS истекает менее чем через 14 дней; WireGuard stale проверять с учётом keepalive и реального трафика, не по одному отсутствию handshake.

У каждого alert: severity, owner, понятное описание, ссылка на runbook, grouping/silence, подтверждение доставки. Проверить тестовым событием «alert → получен человеком → восстановление». Получателя выбирает владелец; не отправлять в клиентские чаты.

### OBS-03. Инструменты поддержки

Сохранить `python -m ops.work_status` и расширить sanitized статусами partial/freshness/uncertain. Добавить безопасные retry/cancel/reconcile операции с RBAC/audit, не ручные UPDATE в production как штатный интерфейс. Любой retry проверяет replay safety и исходную бизнес-идемпотентность.

## 16. BACKUP — независимые копии, PITR и восстановление

P0 перед production cutover. Владелец организует место хранения, исполнитель — настройку и проверку. Пока хранилища нет, реализовать scripts/конфигурацию и испытания на отдельном тестовом repository; не маркировать offsite backup как работающий.

### BACKUP-01. Цели и состав

Предложенные цели для подтверждения владельцем: **RPO ≤15 min, RTO ≤60 min** для БД; для файлов — согласованный сопоставимый recovery point. Это требования для испытания, не достигнутые показатели. Если владелец согласует только ежедневный dump, документировать RPO порядка суток, а не 15 минут.

Копировать:

- PostgreSQL: данные, схема, необходимые роли/расширения и migration state; physical/base backup + непрерывный WAL для PITR, logical dump дополнительно для переносимости/контроля;
- shared artifacts/uploads и metadata consistency; текущие/нужные исторические immutable objects;
- закрытую конфигурацию, ключи расшифровки бизнес-токенов и необходимые secrets — шифрованно и с раздельным контролем доступа;
- release/rollback manifests, проверенные образы или возможность безопасно их восстановить, runbooks;
- Redis AOF при необходимости ускоренного возврата, но источником принятых задач остаётся PG ledger. Кэш можно не резервировать.

Независимость: хранилище вне обоих рабочих узлов, желательно другой физический fault domain и отдельные credentials/администрирование. Физическое расстояние само по себе не защищает от удаления одним скомпрометированным ключом. Предусмотреть versioning/immutability либо ограниченное delete право и защиту retention там, где backend это поддерживает.

Для PITR нужна согласованная цепочка base backup и WAL; один nightly dump не даёт произвольную точку восстановления. Выбрать поддерживаемый инструмент, например pgBackRest/WAL-G или проверенную PostgreSQL-процедуру, зафиксировать версии/совместимость и restore-команды до включения archive mode. [PostgreSQL PITR](https://www.postgresql.org/docs/15/continuous-archiving.html).

### BACKUP-02. Политика и настройка

- Начальная retention для согласования: 7 дневных, 4 недельных, 3 месячных точек; PITR window отдельно. Реальная политика должна сохранять зависимости base/WAL и укладываться в storage budget, не удалять WAL просто по возрасту файлов.
- Шифрование в транзите/хранилище, независимая доступность ключа восстановления, минимальные credentials backup writer и отдельно restore/delete полномочия.
- Archive retry не должен бесконечно заполнять диск без alert. Оценить WAL generation, capacity и отказ offsite; явно описать реакцию на заполнение.
- Настройка `archive_mode` может потребовать restart PostgreSQL: только согласованное окно после свежего backup, с проверкой connections/rollback. Не совмещать без необходимости с первым cutover приложения.
- Schedule backup не конкурирует без лимитов с nightly sync; ограничить IO/CPU и измерить влияние. Проверять exit code, размер, manifest/checksum и возраст, а не только наличие файла.
- Backup secrets не записываются в команды/логи. Отдельная инструкция восстановления доступа к offsite/ключам при потере ноутбука/сервера 1.

### BACKUP-03. Restore drill — обязательная приёмка

1. Восстановить только из независимого repository в изолированную БД/каталог, без чтения текущего PGDATA как источника.
2. Восстановить до заданного времени, проверить schema head, ограничения, контрольные counts/hashes по безопасным таблицам и выборочные бизнес-fixtures.
3. Поднять чистое приложение с outbound sends/payments/AI отключёнными. Проверить login/права, dashboard, report links/artifacts, decrypt тестового токена, jobs/uncertain ledger.
4. Проверить файл/DB consistency и возможность восстановить конфигурацию/ключи. Изолированное приложение не отправляет клиентам накопленные cron jobs.
5. Замерить полный RTO от начала процедуры до проверенного сервиса, а не только время `pg_restore`; RPO — по последней доступной транзакции/WAL.
6. Сохранить обезличенный протокол: backup ID, source cutoff, target, start/end, checks, отклонения, кто принял. Повторять минимум ежемесячно и после существенной смены schema/storage.

Перед реальным восстановлением production отдельно сверять внешние платежи/сообщения/AI operations, произошедшие после выбранной точки: PITR не отменяет side effects у провайдеров.

## 17. OPS — эксплуатация дисков, зависимостей и масштаба

Приоритет P1; изменения дисков/доступа только по согласованному плану.

- Логи Docker/app/nginx имеют size/time retention; временные exports/render profiles и orphan files очищаются безопасным job. Удаление не затрагивает active/pending/uncertain данные.
- Освобождение build cache: inventory → исключить active/rollback artifacts → ограниченная очистка конкретных cache entries → проверить `df`. Не удалять все images/volumes одной командой.
- Расширение root LV на сервере 2: свежий inventory `lsblk/lvs/vgs/df`, тип FS, доступный VG, backup/console/rollback; отдельное изменение, не часть обычного деплоя контейнера. Не использовать старое значение свободного VG без проверки.
- Регулярные security updates хоста/образов/зависимостей через staging и release, с планом reboot. Digest pinning не означает «никогда не обновлять».
- Time sync на обоих узлах, сертификаты nginx, WireGuard unit dependencies, Docker restart/boot order проверены. Новые private ports должны привязываться после появления VPN-адреса; failure не приводит к fallback bind `0.0.0.0`.
- Документировать capacity: max проверенные concurrent users/projects, latency при nightly, RAM/CPU/db-pools, очередь и внешние quotas. Новые серверы добавлять по измеренному bottleneck.
- Триггеры роста: устойчивое нарушение SLO/очереди, CPU/RAM/pool saturation, диск/IO, невозможность выделить manual/AI резерв. Если bottleneck DB, ещё один API может ухудшить ситуацию — сначала агрегаты/индексы/pools.
- P2: отдельный DB-узел/реплика, внешний LB/floating IP, Redis failover и quorum по независимым fault domains. До такого проекта не заявлять автоматический HA; два узла без безопасного quorum/fencing не должны становиться самодельным multi-primary.

Приёмка OPS: оператор без контекста переписки может по runbook развернуть проверенный release, найти причину задержки, безопасно отключить проблемный компонент и восстановить доступ/данные. Инструкции не требуют знания пароля из чата.

### QA-02. Данные и профили нагрузки

- Synthetic tenants с 1/10/30/100 проектами, разные owners/members/ограниченные доступы, папки, направления, paused/deleted scopes, выбранные/удалённые цели, все каналы.

### QA-05. Команды для изолированной image-only проверки

Ниже инструкции, а не выполненный этим документом деплой. Выполнять из чистого source artifact соответствующего релиза, а не из каталога с рабочей `.env`. `RELEASE` — заранее выбранный проверяемый commit, `TEST_IMAGE` — соответствующий собранный образ. Не копировать секреты production в test env.

Пакет исходников из фиксированной ревизии, рабочие изменения не включаются:

```sh
git status --short
git rev-parse HEAD
git log -8 --oneline
git diff --check
python3 -m ops.package_backend "/private/tmp/admirra-release-${RELEASE:?set_commit}.tar.gz" --revision "$RELEASE"
```

Архив распаковать в отдельный каталог, проверить manifest/отсутствие секретов и собрать image с `APP_RELEASE`; точные host path/registry закрепить release pipeline. Для Linux путь временного архива выбрать соответствующий хосту, не предполагать наличие `/private/tmp`.

Из корня распакованного чистого релиза на тестовом Docker-хосте:

```sh
docker build --build-arg APP_RELEASE="${RELEASE:?set_commit}" -t "admirra-devops:$RELEASE" .
export TEST_IMAGE="admirra-devops:$RELEASE"
docker compose -f ops/compose.isolated.yml -f ops/compose.artifact-tests.yml up --abort-on-container-exit --exit-code-from tests tests
docker compose -f ops/compose.isolated.yml -f ops/compose.artifact-tests.yml down
```

Сначала сохранить exit code/log результата tests; cleanup не должен скрыть упавший test-run. Имена тестовых ресурсов фиксированы Compose-проектом, поэтому не запускать несколько таких прогонов одновременно; при необходимости отдельного instance ID сначала согласованно параметризовать project/env. Включённый `ops/run_isolated_tests.py` проверяет `WW_TEST`/`WW_TEST_ID` и изолированный DB host; Compose задаёт эти значения.

Для frontend запускать имеющиеся `npm run build` и тестовые scripts из его package.json, не придумывать несуществующий `npm test`. Визуальная QA — по действующим AGENTS.md проекта; при наличии `.wellwon/canvas/` только через `sh .wellwon/canvas/cv`, в изолированном тестовом instance.

Read-only операционные проверки после соответствующей миграции/конфигурации:

- `python -m ops.work_status` внутри правильного release/container с ограниченными credentials: до миграций таблиц этот вызов не является valid smoke.
- `python -m ops.private_services_check database` / `redis` в одноразовом контейнере с нужным env-file; не выводить env contents.
- `python3 -m ops.check_private_port_exposure` извне проверяет только известные private ports; дополнить ingress/API/IPv6/custom ports после их изменения.
- `/api/health/live`, `/api/health/ready`, test tenant API и публичные домены. `/` HTTP 200 недостаточно.

## 20. Production cutover: допуски и точный порядок

### 20.1. Gates

| Gate | Что должно быть доказано | Что запрещено без gate |
| --- | --- | --- |
| G0 — актуальность | Inventory, отсутствие параллельного deploy, согласованный scope | Любые автоматические server mutations по старым данным |
| G1 — безопасность | Clean release/rollback, secret/access plan, private connections, ресурсный бюджет | Новый runtime с production credentials |
| G2 — корректность | DATA/SYNC/JOB/REPORT/AI тесты, полная handler map, schema compatibility | Реальные новые workers/платные side effects |
| G3 — данные | Свежий независимый backup, restore drill, миграционный/rollback plan | Production migration/cutover |
| G4 — эксплуатация | Метрики/alerts, runbooks, owner окна/получателей, stop criteria | Canary traffic и переключение расписаний |
| G5 — мульти-API | Shared files/state, rights/revisions, SSE/drain, tested nginx | API-2 в публичном upstream |
| G6 — rollout | Single-API worker rollout стабилен, canary LB/нагрузка приняты | Расширение на весь трафик |
| G7 — итог | Две ночи, controlled reports, restore/failure evidence, final DoD | Объявление проекта полностью готовым по этому ТЗ |

### 20.2. Подготовка релиза

1. Зафиксировать окно вне 03:00/05:00 и план уведомления оператора. Проверить активные manual jobs/reports/AI и сроки recurring операций.
2. Сохранить manifest текущего production: images/digests/config версии/port mounts/schema head/расписания. Секреты — только в защищённом backup, не в отчёте.
3. Создать свежую offsite recovery point, убедиться в последнем успешном restore drill. Проверить свободный диск и доступ к console/rollback image.
4. Доставить один проверенный immutable новый artifact и совместимый rollback на нужные узлы; ничего не переключать только от успешного SCP/git pull.
5. Подготовить env с новыми ролями/адресами, проверить permissions, auth keys, schema expectations, global prefix, queue map, provider config и bounded resources. Не печатать `docker compose config` с интерполированными секретами.
6. Сгенерировать новый versioned nginx/config рядом со старым, validate. API-2 вне upstream, новые workers/scheduler ещё не принимают jobs.
7. Проверить test feature flags и исключение клиентских отправок: live smoke только на утверждённых ресурсах.

### 20.3. Переход на durable jobs с одним API

Текущий `work_preflight.py` запрещает запуск при legacy queued/running sync без соответствующего background ledger. Поэтому миграция очереди должна быть реальным отдельным шагом, а не надеждой, что старые задачи «сами разберутся».

1. Включить **реализованный и заранее проверенный** admission gate для новых фоновых действий. Уже принятые jobs остаются видимыми. Если буфер-приём в outbox ещё не реализован на этой совместимой версии, на коротком окне возвращать понятный 503/Retry-After, а не терять запрос/возвращать ложный 202. Не блокировать весь сайт и платежные callbacks без необходимости.
2. Остановить старые producers по карте: API APScheduler и legacy automation ticks; убедиться, что нет выполняющегося tick, который создаст новую batch позже. Disabled schedules сохранить disabled.
3. Дождаться legacy running sync/report/платных действий либо перевести зависшие в документированное состояние после проверки side effects. Для queued выбрать: полностью drain старым consumer при закрытом приёме либо заморозить для переноса после создания новой схемы. Не kill активную отправку как обычный безопасный read.
4. Остановить старый consumer полностью, подтвердить отсутствие его дубликата на обоих узлах. Сохранить перечень оставшихся queued IDs и evidence неопределённых side effects. Не запускать новый consumer на этом шаге.
5. Применить additive Alembic миграции отдельной migration identity. Зафиксировать head, времена/locks и smoke; при ошибке не запускать consumers. Таблицы нового ledger должны существовать до переноса queued jobs.
6. Если legacy queued не drained, транзакционно перенести их в background_jobs/outbox с сохранением IDs/payload/status mapping. Не удалять/обнулять их и не использовать enqueue, который просто дедуплицирует по той же legacy строке без создания ledger. Отдельный повторяемый bridge проверяет соответствие каждой строки; zero orphan legacy jobs подтверждается запросом preflight до запуска workers.
7. Поднять API-1 новой роли с нужной schema expectation, новым DB runtime user, прежними совместимыми auth keys, пока admission gate закрыт. API не выполняет DDL и не запускает scheduler.
8. Поднять ограниченный набор новых workers, выполнить preflight, затем dispatcher/scheduler в согласованном режиме. Сверить calendar cursor: не стартовать все пропущенные side effects автоматически. Scheduler один.
9. Проверить полный цикл одного approved test job: принятие → outbox → claim → факты → revision → UI. Отдельно проверить report/AI без реальных клиентов согласно gate.
10. Открыть приём; наблюдать jobs/DB/ошибки. Увеличивать concurrency только в пределах проверенного manifest.

Если нужен tenant-canary до полного перехода, сначала реализовать явное эксклюзивное routing/ownership между old/new producers/consumers и миграцию конкретной integration. Текущие глобальные флаги не позволяют безопасно «включить Celery для 5%» сами по себе. Без этой реализации использовать описанное короткое контролируемое переключение, а не одновременный old/new consumer на одной очереди/ресурсах.

При rollback после появления durable jobs старый consumer `cdf0a4d` не считается автоматически совместимым. Варианты — возврат подготовленного совместимого clean release либо остановка новых claims и проверенная reconciliation/bridge. Подробности §21.

### 20.4. Включение batching/cache

1. Включить новый read-model сначала на согласованном scope, сравнить с эталонами при тех же revisions/датах. Не shadow-вызывать старый мутирующий GET summary, который меняет visit snapshot; для сравнения использовать чистые функции.
2. Перевести frontend на batch endpoint вместе с совместимым API. Старые endpoints остаются до окончания перехода.
3. Включить aggregate cache отдельным флагом, измерить cold/warm, mutation freshness и SQL load. При ошибке отключить кэш, сохранить новую SQL-схему/данные, включить bounded fallback.
4. Проверить после реального manual sync, смены целей/плана и прав. Наблюдать полную страницу, а не только один быстрый endpoint.

### 20.5. Включение второго API

1. Доказать G5 и достаточный RAM/CPU запас сервера 2 при workers. Запустить API-2 приватно, выполнить cross-replica smoke без публичного трафика.
2. Сначала направить управляемую canary-группу безопасных чтений; mutations только после проверки идемпотентности обоих API. Sticky routing canary не является постоянным решением общего состояния.
3. Этапы приблизительно 5–10% → 25% → целевое распределение; реализовать реальный механизм маршрутизации/weights и измерить фактическую долю. `least_conn` weights сами по себе не гарантируют точного процента при длинных SSE.
4. Наблюдение минимум 30 min на ступень при достаточном числе запросов; при низком трафике добавить контролируемый synthetic smoke, а не считать пять запросов доказательством.
5. После каждой ступени проверить SLO, 5xx, active SSE, pool wait, cache leakage/freshness, job/delivery/AI ledgers. Один critical correctness/security defect останавливает rollout независимо от хорошей latency.
6. Уменьшение доли/исключение upstream выполняется без retry already-started non-idempotent calls; активные streams drain по deadline.

### 20.6. Ночной контроль и закрытие

- Проверить **две последовательные ночи**: плановые integrations/occurrences, успешные/partial/auth failures, очередь, длительности, coverage и пропуски. Ошибка токена не скрывается «зелёным» общим статусом.
- Убедиться, что отчёты не стартуют раньше нужных данных, а default disabled schedules не активировались.
- Выполнить controlled manual report и AI usage smoke в согласованном бюджете; сверить конкретных получателей/operation IDs.
- Сравнить до/после dashboard/summary/folder/dynamics latency под рабочей нагрузкой, зафиксировать cache/DB effect.
- Зафиксировать работающие digests/heads/env-role, завершение legacy retirement, оставшиеся ограничения и следующую capacity ступень. Только после этого убрать временные gates/совместимые маршруты, которые уже безопасно не нужны.

## 21. Откат и аварийные сценарии

### RB-01. Регрессия API или балансировки

Исключить новую реплику из upstream, прекратить приём новых runs на ней, дождаться bounded drain. Сохранить run/job IDs для проверки прерванных действий. Вернуть проверенный совместимый image/config; не делать restore всей БД и не downgrade схему только ради отката API. Если изменён response contract, frontend откатывать к совместимой версии вместе с API.

### RB-02. Ошибка кэша/неверные цифры

Выключить aggregate-cache flag, включить ограниченный чистый DB read путь; при подтверждённой ошибке формулы откатить именно computation version к проверенной. Не выдавать старые значения как новые. Зафиксировать affected scope/revision, проверить детектор/отчёты/AI consumers. Очистка только versioned cache namespace контролируемым способом; broker не трогать, `FLUSHALL` запрещён.

### RB-03. Новый worker работает неверно

Остановить новые claims затронутого kind/tenant; scheduler/dispatcher при необходимости продолжают сохранять backlog, но не отправляют вредные работы в исполнение. Running jobs либо drain, либо fenced recovery после подтверждения состояния. Сохранить ledger/outbox/evidence. Не запускать параллельно старый consumer и не массово переводить uncertain в queued. Возврат только совместимого worker release; для legacy возврата нужен отдельный tested bridge/reconciliation.

### RB-04. Broker/limiter/cache или сервер 2 недоступны

- Cache: bounded DB fallback, circuit breaker, alert.
- Broker: API сохраняет допустимые jobs в outbox; показать задержку. Restore broker/AOF либо создать пустой broker с теми же ACL/prefix и восстановить доставку из PG контролируемым reaper/dispatcher. Не терять uncertain guards.
- Limiter: остановить затронутые внешние запросы; не включать local unlimited fallback.
- Потеря всего сервера 2: API-2 исключить из upstream. API-1 обслуживает доступные DB reads; jobs ждут восстановления, внешние функции могут быть временно недоступны. Это деградация, не полный HA.

### RB-05. БД или сервер 1 недоступны

Защищённые операции fail closed; API-2 не становится независимым рабочим сайтом без БД/ingress. Восстановить инфраструктуру/БД по BACKUP runbook, затем проверить схемы/ключи/files. До replay сопоставить платежи/отчёты/AI side effects с провайдером и локальными журналами. Автоматический пустой primary или restore «последнего найденного дампа» без выбора точки запрещён.

### RB-06. Миграция не проходит

Остановить релиз до старта новых consumers; записать фактическую schema revision/частичные нетранзакционные действия. Транзакционные изменения откатываются штатно; concurrent indexes проверяются отдельно на validity. Вернуть совместимый старый код при допустимой схеме. Если есть новые queued/running/uncertain данные, downgrade с удалением таблиц запрещён. Починка forward предпочтительна, но решение зависит от фактического состояния.

### RB-07. Дубликат/неизвестная отправка или списание

Немедленно отключить автоматическое исполнение соответствующего kind, сохранить provider/request/delivery/transaction IDs и sanitized logs. Проверить внешнее состояние без нового side-effect вызова. Accepted не повторять; unknown — reconciliation с audit/владельцем. Денежную коррекцию выполнять только через разрешённую продуктовую/провайдерную процедуру, не ручным «вернуть число в таблице».

### RB-08. Ошибка firewall/SSH или общий storage

Для сети использовать сохранённую сессию/проверенную консоль и timed rollback только своих изменений; не глобальный flush. Для storage остановить публикацию новых broken artifacts/отправки с ними, оставить доступ к подтверждённым файлам по возможности; восстановить сервис/том и сверить hash/metadata. Не удалять источник миграции до проверки новой копии.

У каждого runbook в итоговой реализации должны быть конкретные service names, безопасные команды, требуемая роль, критерий остановки и контакты. В этом ТЗ намеренно нет универсальной команды «up всё» или destructive restore с production-путём: её можно сформировать только по manifest конкретного релиза.

## 23. Решения/доступы, которые нужны от владельца

Исполнитель заполняет значения и дату согласования; ниже нет заранее выданного разрешения на платные сервисы, реальные списания или рассылки.

| Решение | Предлагаемое направление | Что блокирует отсутствие |
| --- | --- | --- |
| Независимое backup-хранилище, доступ/регион/retention | Вне обоих узлов, защищённое удаление/версии, шифрование | G3 и окончательный cutover |
| RPO/RTO | 15 min / 60 min как цель для проверки | Финальная приёмка восстановления |
| Runtime storage | Приватный файловый сервис на сервере 1 сейчас; adapter позволит подключить object storage позже | Реальное включение выбранного варианта, если нужен внешний доступ/сервис |
| Окно переключения и reboot/PG restart | Вне ночных jobs, с доступной консолью и оператором | Соответствующая операция на production |
| Canary tenant/получатели/AI budget/payment sandbox | Только тестовые/разрешённые ресурсы, лимит расходов | Live smoke, не изолированные tests |
| Куда слать технические alerts и кто дежурит | Отдельный операционный канал, не клиентские чаты | G4 |
| Политика partial reports и AI-prewarm | До решения — не делать неполную автоматическую отправку и не расширять существующий prewarm | Включение изменённой политики, не остальная реализация |
| Ожидаемый рост и release capacity | Пользователи одновременно, проекты/каналы, 7/30/90 days, частота sync | Подтверждение нагрузочной ступени/план масштабирования |
| Разные ли fault domains, backup/console у провайдера | Подтвердить у арендодателя, не делать вывод по IP/RTT | HA-обещания и аварийный план |

Если владелец принимает иной RPO/нагрузку/политику, изменить конкретный requirement и критерии приёмки с записью решения. Не маркировать недоступную внешнюю зависимость как «готово, потому что остальное работает».

### 24.2. Технические основания

Ссылки проверены при составлении ТЗ 11.09.2026. Перед обновлением версий сверить их с фактически закреплёнными версиями проекта; документация `latest/stable` может измениться. Это источники механизмов, а числовые SLO/бюджеты и порядок перехода выше — проектные требования AdMirra, не гарантии производителей.

- Redis ACL ограничивает команды, ключи и Pub/Sub отдельно. Для PSUBSCRIBE нужны разрешённые точные шаблоны; существующие ограничения Celery уже проверены и не должны заменяться admin-доступом. [Redis ACL](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/).
- Broker AOF `everysec` не даёт нулевую потерю последних операций при аварии; поэтому для нашей схемы принят PG ledger/outbox и recovery. [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).
- Настройки redelivery/visibility и shutdown проверять вместе с ограничениями задач, не отдельно от идемпотентности. [Celery Redis](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/redis.html).
- Для nginx поведение retry/buffering/таймаутов и upstream load balancing имеет значение для POST и SSE; используемые возможности сверять с установленной версией, не предполагать функции коммерческого health checking. [Proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html), [load balancing](https://nginx.org/en/docs/http/load_balancing.html).
- PostgreSQL backup/PITR, обслуживание и SQLAlchemy Session semantics — основания требований DB/BACKUP; изменение архитектуры не отменяет их ограничений. [PITR](https://www.postgresql.org/docs/15/continuous-archiving.html), [vacuum](https://www.postgresql.org/docs/15/routine-vacuuming.html), [SQLAlchemy sessions](https://docs.sqlalchemy.org/en/20/orm/session_basics.html).
