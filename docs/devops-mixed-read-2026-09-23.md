# Совместное чтение и запись: найденная гонка сводок

23.09.2026. Локальный candidate, **не production deployment**.
Production API, ingress, БД, env и scheduler не переключались.

## Что обнаружено нагрузкой

В новом `tests/test_mixed_read_workload.py` четыре читателя одновременно
запрашивают настоящие `/dashboard/summary` и `/dashboard/project-summaries`.
Параллельно выполняются 12 durable sync manual/auto и 12 автоматических
AI-комментариев к зафиксированным отчётам, с повторным обращением к каждому
отчёту. Используются 12 синтетических VK-проектов двух владельцев, отдельные
ограниченные SQL pools 5/0, 2/0, 2/0, настоящая PostgreSQL.

Первый запуск выявил **разорванное чтение**: расход **650**, лиды **26**.
При этих фиксированных входных данных расходу 650 соответствуют **25** лидов.
В `READ COMMITTED` синхронизация успела закоммитить следующую версию между
отдельными SELECT расхода и SELECT лидов. Атомарная запись sync сама по себе
не делает набор отдельных SELECT читателя атомарным.

## Исправление `ed31916`

- SQL-only сводки, batch-карточки, списки проектов, дерево, top и folder breakdown
  читают данные в одной короткой `REPEATABLE READ / READ ONLY` транзакции.
  Настройки, доступные проекты, расход, лиды, предыдущий период и каналы берутся
  из одного снимка. Блокировки строк ради чтения не добавлялись.
- Используется тот же Session/слот пула: завершается только предшествующая
  read-only auth-транзакция. Helper нельзя использовать в write workflow;
  pending ORM changes отклоняются, а не теряются. Сессия/изоляция сбрасываются
  при завершении запроса. Метка просмотра дашборда записывается отдельно после
  освобождения snapshot, без попыток UPDATE в read-only транзакции.
- Добавлен детерминированный тест: commit новых cost/conversions точно между
  двумя SELECT. Текущий ответ должен сохранить старую согласованную пару;
  следующий запрос обязан увидеть новую. Проверяется возврат пула к
  `READ COMMITTED`, запрет записи и освобождение соединений при ошибке.
- Исправлен N+1 в сериализации `ClientResponse`: projects → integrations →
  campaigns загружаются пакетно. Для 20 проектов с одной интеграцией каждый
  relationship reads сокращены с **41 до 3 SELECT**, JSON остаётся прежним.
  В эту цифру не входят запросы доступа и агрегаты статистики. Select-in loader
  сам разбивает большие IN-списки на порции; это не обещание трёх SELECT при
  неограниченном количестве проектов. Проверены обычный список, stats, дерево
  с папкой/без неё, отсутствие чужих проектов и токенов в ответе.

### Границы исправления

`campaign_ids` в `/summary` пока сохраняет старый путь точной атрибуции с live
вызовами Метрики. Его намеренно не оборачивали в долгий repeatable snapshot во
время HTTP. Этот пакет не переводит live attribution/dynamics/interactive AI
на detached IO и не закрывает все оставшиеся SQL-over-IO задачи основного плана.

SQL snapshot гарантирует согласованность **одного ответа**, не одинаковый
момент времени нескольких независимых HTTP-запросов. Кеширование, две API
реплики и SSE этим приёмочным тестом не проверяются.

## Что именно имитируется

- HTTP через ASGI TestClient, не внешний ingress и не браузер.
- Sync выполняет настоящие prepare/collect/apply, business status и ledger
  claim/finish; VK API заменён медленным контролируемым адаптером.
- Automatic report выполняет настоящий immutable snapshot/receipt workflow;
  LLM и PDF/PNG renderer заменены медленными заглушками. Финальный snapshot
  проверяется на неизменность; второй запуск не генерирует повторно.
- Проверяется фактическое перекрытие чтений с обоими видами фоновой работы,
  соответствие расходов/лидов, неизменность прошлого периода, 403 для чужого
  batch scope и отсутствие SQL-соединения у конкретного потока в заглушке IO.
- Это **не** real-provider peak, не нагрузка платёжного провайдера, не полноценный
  Celery/broker/cache/SSE/renderer benchmark. Внешняя сеть у test network закрыта.

## Что остаётся после этого пакета

1. Аудит и сокращение тяжёлого list payload; повторный browser-like load по
   согласованным latency/error/pool/queue критериям, а не только статусам 200.
2. Отдельная двухрепличная приёмка cache invalidation/files/upload/SSE/drain,
   работающего Celery/Redis вместе с API, bounded failure/recovery и внешних
   sandbox transports. Существующие unit/recovery tests не равны этому сценарию.
3. Остаток interactive/live SQL-over-IO из основного плана, operator/визуальная
   приёмка pending/uncertain, подтверждение получения алертов и offline key.
4. После приёмки — свежий release/backup/preflight и управляемое переключение.
   Production переключение этим пакетом не выполнено.

S3 и две ночи наблюдения остаются отложены. Логи без тел/контактов сохранены на
server 2 в `/opt/admirra-staging/ed31916/restore-{2db26eb,ed31916}.log` с mode 600.
