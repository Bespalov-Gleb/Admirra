# Устойчивость чтения уведомлений: 24 сентября 2026

## Инцидент и влияние

22:44:07 МСК (19:44:07 UTC): GET `/api/notifications/` завершился 504
через 1.001 с. Request ID `94fb6dce083d1c4f30f2f68e081c956c`.
Nginx зафиксировал `while connecting to upstream` для API2, не ожидание
ответа приложения. Точная причина задержки установления TCP-соединения
не доказана. Перезапуска/OOM API в этот момент не было; соседние проверки
готовности успешны. Это не прежний конфликт блокировок БД.

Начиная с завершения предыдущего переключения в 14:35:25 UTC, до проверки
в 20:22 UTC в ingress-журнале найден один итоговый 5xx. В 19:44:52 UTC
следующее зафиксированное чтение уведомлений успешно (API1, 9 мс);
в 19:47:06 UTC успешно и через API2 (101 мс).

`Header.vue::fetchNotifications` игнорирует ошибку, сохраняет прежний список,
опрос задан раз в 30 секунд (в фоне браузер может задерживать таймеры).
При первом неудачном чтении список остаётся пустым до успешного обновления.
Это запрос колокольчика, а не отправленное пользователем сообщение ИИ,
платёж, синхронизация или генерация отчёта. По этому событию нельзя заключать,
что пользователь потерял результат анализа.

Два critical-алерта относятся к одному событию: Final5xx и агрегатный
MonitorFailed. Они восстановились после выхода ошибки из окна 600 секунд;
это не означает десять минут непрерывной недоступности API.

## Исследование и выбор

- [AWS: ограничение повторов](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html):
  проверять идемпотентность, ограничивать число/время попыток, не умножать
  повторы на нескольких уровнях. Для повторных обращений при перегрузке —
  backoff и jitter. Повтор может усугубить перегрузку.
- [AWS: выбор таймаутов](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/):
  опираться на измеренную задержку зависимости и допустимую долю ложных таймаутов,
  учитывать сетевые задержки. «Универсального мирового значения» нет.
- [Nginx: proxy_next_upstream](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_next_upstream):
  переключение допустимо до передачи ответа клиенту; автоматические повторы
  неидемпотентных действий опасны. `proxy_read_timeout` — интервал между
  чтениями, а `proxy_next_upstream_timeout` — окно допуска следующей попытки,
  **не жёсткий дедлайн всего ответа**.

Наш выбор: connect 1 → 3 секунды для балансируемых API-маршрутов.
Это начальный эксплуатационный запас для единичной задержки, не доказанный
оптимум p99.9. Нормальные ответы не задерживаются искусственно. Если сервер
реально недоступен, обнаружение может занять на две секунды больше — поэтому
для небольших проверенных чтений применяется один failover на вторую реплику.
Для длительных задач/ИИ/изменений универсальные повторы не добавляются.

## Точный scope

1. Добавлен **exact** `/api/notifications/` рядом с существующим exact
   `/api/notifications`. Пропущенный завершающий слеш обходил safe-read policy.
2. Только GET/HEAD входят в safe-read pool; остальные методы через существующий
   named location с `proxy_next_upstream off`. Проверена сохранность POST/body/query.
3. В safe-read snippet: connect 3 с, send 2 с, read-gap 5 с, всего максимум
   две попытки, окно допуска повторной попытки 12 с. Повтор только на
   error/timeout/invalid_header/502/503/504, не 401/403/429/500.
4. В generic `/api/` и assistant conversations connect 3 с;
   прежние read/send 120 с и **retry off** сохранены.
5. `/notifications/read-all` и `/{id}/read` не входят в exact location.
   Платежи, отчёты, синхронизация, ИИ не повторяются балансировщиком.
6. Нет новых кэшей персональных данных, миграций, рестартов приложений,
   смены весов, изменений worker-конфигурации или frontend.
7. Shared safe-read snippet также подключён старым virtual host `.online`:
   его connect тоже станет 3 с; сам legacy site-файл не изменяется.

Это один немедленный переход на другую реплику на уровне балансировщика,
не цикл повторов на одном сервере. Дополнительные браузерные повторы не
добавляются. Jitter для регулярного polling можно рассматривать отдельно при
росте числа клиентов, но он не исправляет ошибку сопоставления маршрута.

## Проверка и выкладка

`tests/test_read_transport.py`: policy/idempotence/drift tests и отдельный
Nginx со случайными loopback-портами, временным pid/config, двумя mock API.
Явно требуется `WW_TEST=1 WW_TEST_ID=read-transport-20260924`.
Проверяются 503, отказ соединения, таймаут чтения, отказ обеих реплик,
401 без повтора, оба варианта URL и HEAD, отсутствие повторов mutations/ИИ.
Ни один реальный API для fault injection не отключается.

Выкладка на ingress:

```sh
python3 -m ops.api2_canary.harden_read_transport apply \
  --root /etc/admirra/releases/read-transport-20260924
```

Скрипт сохраняет root-only before/after, отказывается перезаписывать drift,
проверяет `nginx -t` и делает graceful reload. При ошибке валидации/reload
восстанавливает исходные файлы. API/worker/frontend контейнеры не трогает.

Откат из того же каталога с кодом:

```sh
python3 -m ops.api2_canary.harden_read_transport rollback \
  --root /etc/admirra/releases/read-transport-20260924
```

После выкладки: авторизованные чтения уведомлений на двух API и публичном
домене (без вывода содержимого/токена), readiness, алерты, ingress-журнал.
Алерты не отключать: успешный fallback по существующей политике ещё может
дать warning, итоговый 5xx — critical. Правка снижает влияние краткого сбоя,
но не гарантирует отсутствие сетевых отказов и не заменяет их расследование.
