# Регистрации Яндекс/MAX → Метрика, 25.09.2026

## Подтверждённая причина

Read-only аудит production: пять новых пользователей Яндекс за 25 сентября,
у всех отсутствуют metrika_client_id/yclid. Marketing counter 109911357:
33 визита, signup_complete=0, trial_start=0, signup_start=4, signup_offer_click=1
на момент диагностики. Цель «Регистрация завершена» 571173208 настроена на
signup_complete, «Старт триала» 571173268 — на trial_start. Эти настройки не менялись.

Фактический startYandexLogin ведёт на `/auth/yandex/callback`, где не было
аналитики, хотя `/auth/login/yandex/callback` её содержал. Production chunk
YandexCallback-Dagps99n.js совпал по SHA256 с исследованной сборкой.
У MAX аналогичный пропуск, плюс backend всегда возвращал is_new_user=false,
а response schema вовсе не содержала поле.

## Исправление

- Общий tracker для Яндекс, VK, MAX. Только server is_new_user===true вызывает
  signup_complete, legacy signup и trial_start, с method провайдера.
  Fallback по возрасту аккаунта удалён; логин/привязка не являются регистрацией.
- Дедуп внутри вкладки и sessionStorage по аккаунту/провайдеру/событию.
  Отсутствующая очередь ym не отмечается как успешная отправка. Это не durable
  outbox: блокировщик/недоступность Метрики всё ещё могут помешать доставке;
  вызов reachGoal не доказывает появления конверсии в отчёте.
- Сохраняем ClientID/yclid после OAuth. MAX завершает polling раньше установки
  токена вызывающей страницей, поэтому identity fetch получает явный токен из
  завершённого ответа, без подмены старой сессией Axios. Таймаут 5 s; ошибки
  аналитики не блокируют авторизацию. Сбор ClientID ограничен 3 s.
- У MAX одноразовая сессия хранит явный is_new_user. Новый пользователь=true,
  существующий/привязка=false. Повторный webhook не меняет уже авторизованный
  аккаунт/флаг; конкурентные status polls сериализованы row lock.
- Никаких новых целей, фальшивых регистраций или backfill в боевую Метрику.
  Пять старых регистраций не восстановлены: нет сохранённых attribution IDs.
  Старые вкладки должны перезагрузить приложение, чтобы получить новый callback.

## Проверки

- 7 Node-тестов tracker: провайдеры, новые/существующие, несколько аккаунтов,
  недоступное хранилище/счётчик, ошибки identity.
- Изолированный Chromium: 15 сценариев настоящих callback-компонентов и MAX
  composable; new/old/отсутствующий флаг, linking, подключение рекламного кабинета.
  Проверены точные названия целей, counter ID и Authorization identity-запроса.
  Всё внешнее IO заблокировано, ответ провайдеров и Метрика подменены.
- Регрессия онбординга: четыре ширины, темы, карточка, скидка, навигация — passed.
- Candidate a58b2ff: 112 backend-тестов на изолированном PostgreSQL passed.
  Финальный candidate/результат приёмки записаны ниже после rollout.

## Порядок схемы: важно для следующих релизов

`max_oauth_login_attempts.is_new_user boolean NOT NULL DEFAULT false` добавлен
как **expand-фаза**, без изменения сохранённых пользователей/сессий.
Alembic version production остаётся **f68b92a3b4c5**: этот контракт зафиксирован
в EXPECTED_SCHEMA_REVISION всех API/воркеров и мониторинге.

Нельзя запускать `alembic upgrade head` отдельно от согласованного обновления
этих контрактов. Миграция f79ca3b4c5d6 допускает уже добавленную колонку, чтобы
позже завершить переход версии без повторного ALTER. Helper
`ops/migrate_max_signup_flag.py` теперь только добавляет/проверяет колонку и
**не двигает version_num**. Ему нужна роль владельца таблицы; у API DDL прав нет
и они не выдавались. Lock timeout 2 s, statement timeout 10 s.

Во время первой попытки был преждевременно продвинут version_num: startup API2
и мониторинг отказали по schema mismatch. API2 был выведен из пользовательского
upstream, activation откатил image на 6233284. Метка возвращена на f68b92a3b4c5,
полезная совместимая колонка сохранена. Оба API снова ready. В canary access log
с 12:02 UTC до контрольной проверки новых 5xx=0; monitoring alerts действительно
были, их не отключали. Исправлен helper, добавлен тест сохранения старого контракта.

## Production и откат

Backend rollout — поочерёдно, drain API2/API1 с завершением старых Nginx workers.
Не изменять runtime env/worker images, не отключать schema guard/alerts.
Frontend overlay сохраняет landing/legal и предыдущие chunks.
При rollback кода оставлять колонку и version_num=f68b92a3b4c5.
Полное подтверждение рекламной конверсии — после **новой реальной регистрации**:
увидеть signup_complete в Метрике и сохранение attribution IDs, а затем проверить
в Директе именно выбранную цель 571173208. Боевые тестовые конверсии не посылались.
