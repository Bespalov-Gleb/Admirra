# Скидка за первое подключение и ecommerce Метрики

Дата: 22.09.2026. Production-релиз выложен, **скидка включена для всех подходящих trial-аккаунтов** по указанию владельца. Check включён в существующем live-сайте CloudPayments. Реальная оплата и отдельная строка в полученном чеке пока не проверены.
Исходные ТЗ: `admirra_signup_discount_tz.html`, `admirra_metrika_ecommerce_tz.html`.

## Реализовано

- Один показ окна после регистрации/первого входа в действующий trial; показ фиксируется сервером. Плашка под хедером до подключения и после выдачи скидки. Текст запроса доступа для клиента с копированием.
- Первое завершённое подключение Директа, VK Ads или Avito Ads выдаёт один грант владельцу биллингового аккаунта. Черновик/отдельная Метрика не выдают скидку. Повторное подключение не продлевает срок. Массовый импорт кабинетов также учитывается.
- Скидка 20% только на первую оплату self-service тарифа, срок — конец текущего trial. White Label остаётся по заявке. Дополнительные слоты не дисконтируются. С промокодом не суммируется.
- Годовая цена: минимум между обычной годовой ценой и 80% от 12 месячных платежей. Для «Агентство»: 5 520 ₽ месяц / 66 240 ₽ год; продление — 6 900 ₽ / 69 000 ₽. Текущий прайс берётся с сервера.
- Вместо старого winback 25% при включённой новой функции. При выключенном флаге старый механизм сохраняется.
- Check callback валидирует подпись, владельца, сумму, валюту, актуальность заказа и срок гранта. Один Check резервирует один платёж; смена заказа во время обработки блокируется. Fail освобождает резерв, не сжигает скидку и действующий trial. Pay потребляет грант.
- Первоначальная цена и версия прайса сохраняются в заказе. Полная цена и полный чек для следующего рекуррента передаются отдельно; повторный InvoiceId от CloudPayments не заставляет повторно применять скидку.
- Письмо за два дня до конца trial: текстовая и HTML-версии с кнопкой тарифа, максимум 50 за проход, одно письмо на пользователя, без SQL-транзакции во время SMTP. Реализованы legacy scheduler и durable maintenance.
- Ecommerce отправляется только после принятого сервером Pay. ID покупки — TransactionId; реальные сумма, тариф, период, скидка и версия прайса — из серверного snapshot. В браузерной аналитике нет email/телефона/ID пользователя.
- Стабильные SKU: start, basic (Агентство), standard (Про), white_label + month/year. Изменение названия тарифов не меняет SKU.
- Дедупликация в памяти и sessionStorage; восстановление ожидания оплаты после перезагрузки; ограниченное ожидание callback аналитики. Повторный рекуррент не подменяет первую покупку в confirmation endpoint.
- Автопродления, отдельная докупка слотов, отказы, возвраты и неоплаченные заказы не создают браузерный purchase. При блокировщике/отсутствии Метрики оплата не ломается. Счётчик приложения и purchase разрешены только на admirra.ru/www.admirra.ru.

## Отдельная строка скидки в фискальном чеке

Требование владельца: именно в чеке, не только в интерфейсе оплаты.

В CustomerReceipt добавлены:

```json
{
  "userRequisiteData": {
    "requisiteKey": "Скидка за подключение 20%",
    "requisiteValue": "1 380,00 ₽"
  },
  "additionalReceiptInfos": ["Скидка за подключение 20%: 1 380,00 ₽"]
}
```

Это дополнительный реквизит пользователя (ОФД 1084/1085/1086) и отдельная информационная строка. Не отрицательная товарная позиция. Позиция тарифа уже имеет уменьшенную цену; сумма Items совпадает с оплатой. Полный рекуррентный чек скидку не содержит.

Поддержка полей описана в [CloudKassir CustomerReceipt](https://developers.cloudkassir.ru/#customerreceipt). **Перед активацией обязательно получить тестовый чек через используемую связку CloudPayments/CloudKassir и проверить его фактическое отображение.** Передача полей в JSON не доказывает их печать в конкретном шаблоне кассы/ОФД. Реальный чек пока не получен.

## До включения на production

1. Собрать отдельный проверенный релиз. Не деплоить весь dirty worktree: рядом незавершённые DevOps и пользовательские изменения лендинга/мобильной вёрстки. Проверить фактические версии API1/API2/automation и миграций.
2. Сделать проверенный backup БД. Миграция `ef1a2b3c4d5e` зависит от `de0f1a2b3c4d`; не запускать вслепую `alembic upgrade head` поверх старой production схемы. Для узкого релиза применяются только 8 nullable полей users и индекс из этой миграции, в транзакции с lock_timeout 2s, statement_timeout 15s. Alembic head остаётся `cc3d4e5f6a7b`; идемпотентный upgrade позже примет эти поля в общей цепочке. Никакие остальные DevOps DDL не запускаются.
3. Выкатить совместимый API1 и старый automation с `SIGNUP_DISCOUNT_ENABLED=false` и пустым `SIGNUP_DISCOUNT_PILOT_USER_IDS`. API2 остаётся без изменений: nginx направляет на него только часть `/api/auth/me`, `/api/clients`, `/api/folders`, `/api/notifications`. Все billing/integration endpoints идут на API1. При будущем расширении балансировки сначала обновить API2. В текущем legacy runtime **нет** `/api/health/ready`: проверять OpenAPI, protected routes, read-only ORM, HTTP страниц и подпись Check.
4. **По решению владельца использовать существующий live-сайт `admirra` в CloudPayments, новый сайт/терминал не создавать.** Перед пилотом настроить Check URL `https://admirra.ru/api/billing/cloudpayments/check`, HTTP POST, HMAC; Pay/Fail/Recurrent/Cancel и действующую фискализацию оставить без изменений. Check действует на весь терминал: проверить совместимость обычных оплат/продлений/слотов/привязки карты, а не только скидки. **Не включать скидку до подтверждённой работы Check.**
5. Проверить тестовый чек: отдельная строка скидки, правильный итог, email покупателя, отсутствие скидки в следующем рекуррентном чеке. Если провайдер не переносит поля — выяснить поддерживаемый путь у CloudKassir, не подменять задачу строкой только в UI.
6. Владелец сообщил, что Метрика 109911357 настроена; повторно менять настройки не требуется. Для optional goal_id получить реальные числовые ID целей `payment_success` и `plan_upgrade`; при сборке задать `VITE_YM_PAYMENT_SUCCESS_GOAL_ID`/`VITE_YM_PLAN_UPGRADE_GOAL_ID`. Без значений purchase отправляется без optional goal_id. Не подставлять ID из примера ТЗ.
7. Проверить цели signup, discount_modal_shown, discount_modal_clicked, cabinet_connected_first, subscription_paid. Уведомления о регистрации/способе VK не относятся к этой доработке, они уже исправлены ранее.
8. Выбрать согласованный аккаунт без прошлых оплат с действующим trial; добавить только его UUID в `SIGNUP_DISCOUNT_PILOT_USER_IDS` на API1/automation. Не менять платёжную историю и не сбрасывать действующий тариф ради теста. Перед реальным списанием согласовать с владельцем тариф и точную сумму; сама выкладка не разрешает списание. Проверить один purchase, фактическую выручку и товар в «Заказах» Метрики, reload без дубля, блокировщик, отмену/ошибку, апгрейд. Старые офлайн-конверсии не превращались в серверный ecommerce; общая выручка автопродлений в ecommerce — отдельная задача из раздела 9 ТЗ.
9. После приёмки включить флаг на всех участвующих процессах, пересоздать только нужные сервисы. Проверить нового пользователя: регистрация → подключение → toast → цены → подтверждённая оплата → исчезновение плашки. Действующие платные аккаунты не получают предложение.
10. Проверить одно напоминание на синтетическом trial, не массовую отправку настоящим пользователям.
