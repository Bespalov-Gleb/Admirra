# DB-02 / очередь — публикация без открытой SQL-транзакции

Часть T03/T08. Новый runtime пока не включён на production; миграция для этой правки не нужна.

## Изменение

Раньше scheduler вызывал `app.send_task` внутри транзакции, удерживая соединение PostgreSQL и блокировки outbox на время подключения/отправки в Redis. Теперь:

1. Короткая SQL-транзакция резервирует до 10 записей через `FOR UPDATE SKIP LOCKED`, устанавливает срок 120 секунд и увеличивает поколение попытки; commit.
2. Отправка в Redis проходит вне SQL-сессии.
3. Отдельная короткая SQL-транзакция подтверждает только актуальное, ещё не истёкшее поколение. Для успешно опубликованной queued-задачи следующий повтор через 30 секунд.

Существующее поле `publish_count` теперь явно означает число **резервирований транспортной попытки**, не число успешных отправок и не количество бизнес-исполнений. `next_publish_at` до подтверждения служит сроком резервирования. Время берётся из PostgreSQL. Новых столбцов нет.

## Сбои и гарантии

- Rollback резервирования делает запись сразу доступной другому publisher.
- Смерть процесса до отправки или после принятия брокером не удаляет запись: после 120 секунд она доступна для повтора.
- Неизвестный результат транспорта или ошибка SQL-подтверждения не трактуются как гарантированная неотправка.
- При сбое в середине batch оставшиеся записи ждут истечения резервирования (до 120 секунд). Это ограниченная задержка, не потеря задания.
- Устаревшее подтверждение проверяет одновременно generation, deadline и актуальное время; не может отложить уже перехваченную попытку.
- Завершённое задание удаляет outbox; поздний ответ Redis не воссоздаёт запись.
- Потеря Redis не теряет committed PostgreSQL jobs. Повторные сообщения допустимы — бизнес-исполнение защищают существующие claim/lease/fencing, а не транспортный publish.

Не обещаем exactly-once доставку во внешний мессенджер. Не меняем защиту отправок отчётов и uncertain reconciliation.

## Проверки

`tests/test_outbox_publication.py`: во время транспорта `pool.checkedout() == 0`; независимая SQL-сессия берёт строку `NOWAIT`; два publisher получают разные batch; rollback, позднее подтверждение, завершение задания до подтверждения, частичная отправка, ошибка подтверждения. Два теста действительно завершают отдельный процесс через `os._exit` до/после принятия сообщения и проверяют сохранность outbox.

`test_celery_recovery.py` теперь запускает первый реальный Redis → Celery вызов именно через новый publisher, затем проверяет падение дочернего worker, восстановление и дубликаты. Старые durable/backfill tests обновлены под границы транзакций; приоритет ручной синхронизации сохранён.

Первый targeted прогон до добавления двух process-death cases: **37 passed**, 16 warnings, 5,13 s. Финальный полный source-bind regression: **420 passed, 1 skipped, 1 deselected**, 47 warnings, 79,98 s. Проверка чистого committed image — следующий отдельный шаг.
