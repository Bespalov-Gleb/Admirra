# Полнота данных: Google Sheets, AI и детектор

Статус: **локальный candidate, не production**. Продолжение `fe76bd9`.
Новых миграций в этом пакете нет; требуется уже подготовленная схема
`f13c4d5e6f70` (включая `sync_coverage`). Не выкладывать поверх старой production
схемы простым pull/build/up.

## Общий контракт

`core.consumer_freshness.verify` проверяет integrations/settings/stages и
непрерывность покрытия точного диапазона. Сначала client → integration locks
в устойчивом порядке; SQL-only, без собственного commit. Revision включает
окна coverage и execution/observed_at: обновление фактов при тех же настройках
также инвалидирует производный результат. SUCCESS/last_sync_at и наличие
строк сами по себе не являются подтверждением полноты.

Три независимых флага, по умолчанию **false**:

- `SHEETS_FRESHNESS_GUARDS`
- `AI_FRESHNESS_GUARDS`
- `DETECTOR_FRESHNESS_GUARDS`

Каждый требует `REPORT_FRESHNESS_GUARDS=true`, `DURABLE_TASKS=true` и
`REPORT_DELIVERY_GUARDS=true`. Неверная комбинация отклоняется при старте.
Порог возраста доказательства — `REPORT_DATA_MAX_AGE_MINUTES`, по умолчанию
1440, максимум 1440. Ограничения: 200 проектов, 512 источников,
4096 пересекающихся окон на источник/набор стадий, диапазон менее 7320 дней.

## Google Sheets

Календарный project child и ручной export сначала готовят полный, ограниченный
по размеру снимок в отдельной SQL-сессии. SDK и запись запускаются после
закрытия этой сессии. Проверяются вся Raw Data / Goals история и периоды
Weekly Reports / Monthly Report, включая текущий отчётный период до сегодня.

Недельные/месячные суммы пересчитываются через общий StatsService внутри
проверенного среза, а не берутся на доверии из старой таблицы агрегатов.
Пересчитанные значения остаются в снимке: генераторы с внутренним commit не
вызываются. Старые отчёты в БД не переписываются этим guarded path.
Непрерывная недельная/месячная история восстанавливается из диапазона фактов
и старых ключей, поэтому новый недельный отчёт не теряется при смене недели.

Сохранены четыре листа и формат колонок. Лимиты: 50 000 строк / 8 MiB по
умолчанию, 16 384 символа на текстовую ячейку, максимум 256 исторических
недельных+месячных периодов для пересчёта. Проверяется и итоговый размер после
пересчёта. Частичный успешный экспорт вместо полной истории запрещён.

Отказ до записи: отсутствующая coverage, неактивный/сменившийся owner/scope,
будущие факты, строки без привязки к интеграции, исторические цели вне
текущего набора выбранных целей, превышение лимита. Это не удаляет старые
строки Google-таблицы. Перед записью повторно проверяются owner, назначение
таблицы и revision. Ручной путь сообщает HTTP 409; worker получает
`RejectedBeforeExternalIO`, а не ложный success или автоматическую повторную
запись после неизвестного исхода. Ошибка Google после начала записи остаётся
неопределённым внешним исходом, как в существующем durable контракте.

Legacy методы отдельных листов при включённом флаге направлены через полный
проверенный экспорт. Частичный Goals-export по integration_id отклоняется.
`write_snapshot` — низкоуровневый writer, не публичный путь чтения БД.

## AI

DB-backed комментарий, полный отчёт и прежний чат получают detached-контекст
через отдельный coverage capture (текущий + предыдущий равный период).
До проверки модель не вызывается. После ответа повторно проверяются revision
и сам контекст; если они изменились, результат отклоняется, без автоматического
повторного платного запроса. Уже состоявшийся вызов провайдером оплачивается:
этот пакет не реализует возврат денег или durable paid-request ledger.

Кэш хранит `data_revision`; старый кэш без неё не повышается автоматически
до verified. Перед записью комментария revision снова проверяется **в той
же транзакции**, которая сохраняет кэш. API генерации возвращает 409 при
неполноте; чтение кэша — `text=null`, `stale=true`, `waiting_data`/`regenerate`.
Прогрев и старый ночной генератор используют тот же контракт публикации.

Legacy since-last-visit snapshots, AI memory и непроверенные detector flags
не подмешиваются как подтверждённые факты. Запись старой memory при включённом
AI-флаге приостановлена; нужен отдельный revision-aware контракт её возврата.
Ошибки чтения направлений не скрываются пропуском блока в verified prompt.
Диагностический лог реального платного вызова сохраняется и при последующем
отказе публикации.

Новый чат `/ai/assistant` работает с **live API**, а не со статистическими
таблицами. Для него DB coverage неприменима. Добавлена совместимая metadata
в ответах инструментов (не требует флага): Direct сообщает об усечении 200
строк; Метрика сохраняет sampled/sample_share и неполноту разбивки; Авито
показывает отсечение кампаний/строк. Playbook запрещает считать частичные строки
полным итогом и трактовать `no_rows`/ошибку как доказанные нули. VK уже имел
раздельные totals/page/no_rows; регрессия сохранена.

## Детектор

Проверка выполняется **до** baseline, закрытия старых алертов, upsert,
recovery counters и уведомлений. Требуется самый широкий используемый lookback
(baseline + fresh + skip, CPL, баланс, stopped/tracking) и начало активного
плана. При неполноте возвращается False: существующие алерты/счётчики не
изменяются и гипотезы не запускаются.

Новые кандидаты получают data_revision в meta. Sidebar summary скрывает
неподтверждённые текущие выводы с нейтральным sync issue, не удаляя историю.
KPI plan context, прошлый plan completion и подсветка кампаний также проверяют
свои диапазоны. Это не изменение трёхдневного plan warmup и не «выздоровление».
Durable LLM enrichment проверяет revision при подготовке и перед применением
ответа вместе с прежней подписью alert. Legacy LLM-in-transaction путь при
включённом detector-флаге отключён.

## Проверки

Изолированный Compose project `admirra-consumer-freshness-20260922` на server 2:
синтетические PostgreSQL/Redis, internal network, WW_TEST=1, без provider IO,
ключей пользователей, реальной доставки и платежей. Git `fe76bd9` + точечные
изменения; зависимости из `admirra-devops:3d65ef3`. Это не собранный immutable
release artifact. Окончательный прогон: **240 passed, 19 warnings, 145,68 s**.
Набор: consumer_freshness, direct_export_freshness, sheets_snapshot,
calendar_work, sync_detector_isolation, detector_hypothesis_work,
ai_comment_prompt_v2, assistant_vk_reporting, detector_iteration3,
detector_novelty_iteration4, runtime_roles, report_route_guards,
report_freshness. Промежуточные прогоны: 187, 238 и 75 passed (пересекающиеся
наборы, не суммировать). Compile и `git diff --check` пройдены.

Покрываются пропуски coverage, историческое окно, смена source revision во
время AI, блокировка публикации устаревшего кэша, запрет SDK до готовности,
непривязанные/невыбранные факты, повторный контроль назначения таблицы,
сохранение старых алертов, отмена устаревшей LLM-гипотезы, API 409,
неполные live-ответы и совместимость выключенных флагов.

## Что это НЕ закрывает / условия включения

1. Не включать флаги рядом с legacy writers. Сначала миграции, drain, durable
   ownership, заполнение coverage; затем проверка готовности реальных периодов.
2. Обычная nightly синхронизация по умолчанию обновляет только 7 дней. Она
   **не обеспечивает** свежую 51-дневную baseline или многолетнюю Sheets
   историю. Нужен bounded refresh scheduling/budget для этих consumers либо
   отдельно согласованная политика возраста закрытых исторических периодов.
   Этот пакет сам массовый refresh не запускает: длинный неподтверждённый
   диапазон останется waiting/409. Поэтому включать всё сразу сейчас нельзя.
3. Для больших Sheets историй нужен spool/chunks; для legacy orphan/unselected
   rows — контролируемая миграция/пересинхронизация, не молчаливое исключение.
4. Нет атомарной транзакции PostgreSQL+Google. После последней проверки
   источник может обновиться; отправляется уже зафиксированный снимок.
   Общий resource/order/reconciliation протокол внешних записей остаётся.
5. Закрыты SQL-сессии **подготовки**, не все session lifetime в старом API:
   request/auth Session может существовать во время HTTP. Ночной legacy
   AI-loop ещё не заменён bounded durable paid ledger; ai.prewarm выключен.
6. Нужны UX-приёмка waiting/409, полный regression окончательного образа,
   restore/migrations, mixed-load с измерением locks/latency/provider budget,
   разрешённый end-to-end и затем согласованный cutover. Не заменять эти gates
   успешным синтетическим тестом.

Production не менялся. S3 и две ночи наблюдения остаются отложенными владельцем.
