# Scoped recurring: SQL/IO и подтверждение состояния

Кандидат `5f192f2`, 21.09.2026. **Не выложен в production.** Рабочие backend/automation, схема, цены и доступный canary не меняются. Продолжение BILL-01, не его полное закрытие.

## Исправление

Раньше `billing.recurring` передавал ORM-подписку в платёжный helper и держал SQL-соединение во время CloudPayments HTTP. Затем мог снять `recurring_sync_required`, хотя пользователь уже изменил подписку. Теперь scoped child:

1. Читает строго подписку + владельца, проверяет необходимость обновления, действующий provider ID и отсутствие отмены. Фиксирует копию всех полей строки, email и рассчитывает прежним алгоритмом тариф/период/слоты/снимок прайс-бука.
2. Закрывает сессию. Отдельно перепроверяет состояние после подготовки и валидирует worker lease до HTTP. Изменение до вызова означает skip без обращения к провайдеру.
3. Вызывает прежний helper с отделёнными от ORM значениями. SQL-соединение и row lock во время этого вызова не удерживаются.
4. На успешный ответ открывает короткую транзакцию, блокирует актуальную строку, сверяет весь снимок и email. Только для неизменённой подписки очищает флаг. Commit защищён worker lease.

Если состояние изменилось во время HTTP, результат — `BillingMaintenanceUncertain`, а не успешное согласование нового состояния. Timeout/неподтверждённый ответ тоже не снимает флаг. Не-replayable durable job переходит в `uncertain`; redelivery и новый календарный occurrence по тому же resource не выполняют новый вызов до явной сверки.

Полная сверка строки намеренно консервативна: даже стороннее изменение служебного поля может потребовать сверки, вместо попытки угадать актуальность результата. Снимок не записывается в очередь/логи; его долговременное хранение в журнале операций остаётся частью следующего контракта.

## Оставшаяся граница безопасности

Этот пакет **обнаруживает**, но не предотвращает конкурентные внешние операции старого interactive API. Например, update в CloudPayments может закончиться после отмены и затронуть provider state, даже если локальное подтверждение отклонено. До включения новых billing workers нужны общий durable intent/порядок update/cancel, сверка по provider ID, обработка crash после внешнего успеха и операторский путь разрешения `uncertain`. Автоматическую компенсирующую отмену без сверки не добавляли: она тоже может конфликтовать с новой подпиской.

Проверено по [официальной документации CloudPayments](https://developers.cloudpayments.ru/), раздел «Изменение подписки на рекуррентные платежи»: изменение атрибута отменённой подписки снова активирует её; поддерживаемые интервалы — Day, Week, Month. Поэтому локального отказа в commit после гонки недостаточно, а существующий годовой интервал Month/12 сохраняется.

Legacy глобальный handler сохранён для текущего production scheduler; его SQL/HTTP поведение этим scoped-пакетом не изменено. Нельзя включать оба календаря параллельно. Общая карта: [оставшийся DevOps](devops-remaining-2026-09-20.md).

Следующий финансовый пакет должен охватить вместе `/billing/autorenew/cancel`, тарифные/slot update paths и recurring child: durable intent с ожидаемыми provider ID/параметрами, общий порядок операций по подписке, проверка неопределённых исходов по провайдеру, audit разрешения конфликтов. Одного SQL row lock в подтверждении или отдельного mutex только у worker недостаточно. До такого пакета новые recurring consumers не включать.
