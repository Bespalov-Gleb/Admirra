# Статистика телефонии: изоляция владельца и bounded SQL

Candidate, 22.09.2026. Production не менялся. Новых миграций и внешних вызовов нет.
Этот пакет закрывает два read endpoints, не весь lead pipeline.

## Исправлено

- `GET /lead/stats`: вместо общего JSONL-файла читает только сохранённые `Lead`,
  связанные с `PhoneProject.owner_id` текущего пользователя. Параметр даты
  проверяется FastAPI; произвольный путь к файлу больше не используется.
- Дата означает календарный день UTC, интервал `[00:00, следующие 00:00)`.
  Возвращаются точный total, до 100 категорий причин, `other_count` и явный
  `by_reason_truncated`. Причины группируются до первого `:`, без подробного
  ответа провайдера; длина категории ограничена 200 символами.
- `GET /phone-stats/`: один SQL-запрос вместо четырёх. Итоги и таблица проектов
  строятся из одного согласованного результата без чтения телефонов, email,
  form_data или всех лидов в память. Существующий JSON-контракт сохранён.
- Только завершённые `VALID`/`INVALID`/`SPAM`; `PENDING` не является отказом.
  Отклонение — `INVALID`/`SPAM` или `is_spam=true`, как в scoped daily/weekly alerts.
  Старое потенциально противоречащее `is_valid` больше не определяет счётчики.
- Период статистики 1–365 дней, с исключённой правой границей; будущие записи
  не учитываются. Не более 1000 проектов в результате; при превышении — HTTP 422
  с требованием уменьшить период, а не частичный итог. В SQL читается до 1001 строки.
- Проверка owner выполняется в том же SELECT, что агрегация. Нет кэша привязки,
  общего process-local состояния, обращений к Redis или внешних API.

## Проверки

Изолированный PostgreSQL, internal Docker network, `WW_TEST=1`; синтетические
пользователи и лиды. Тесты покрывают изоляцию/смену владельца, полуоткрытые даты,
PENDING, конфликт status/is_valid, пустые данные, точный total при ограничении
причин, отказ от частичной таблицы, один SQL statement, HTTP auth/date/bounds.
Финальный прогон: **48 passed, 17 warnings**, 43,24 с (`test_lead_scoped_stats`,
`test_lead_alert_work`, `test_api_role_boot`). Exit code 0. Локальная компиляция
Python и `git diff --check` также прошли. Предварительный прогон выявил порядок
валидации аргументов и ошибку импорта тестового модуля; оба исправлены до финального
прогона. Полный manifest 1281 из предыдущего пакета заново здесь не запускался.

## Что остаётся

- `GET /reports/quality` и `/reports/blacklist` всё ещё используют legacy global
  analytics/Redis. Не считать всю страницу PhoneReports исправленной этим пакетом.
- Для чёрного списка нужны ключи/ledger с owner+project, bounded генерация по
  сохранённым данным, безопасная проверка в UTM validator и scoped чтение.
  Старые общие записи нельзя автоматически приписывать конкретному владельцу.
- Не все ранние ветки отклонения передают project/db в `_reject`. Поэтому новая
  статистика честно отражает **сохранённые** проектные лиды, но не восстанавливает
  несохранённые отказы из общей памяти/логов. Источник явно указан в `/lead/stats`.
  Следующий пакет должен сохранять результат каждой проверки с project binding,
  без включения ненадёжных повторных CRM/email/Telegram side effects.
- Валидация/немедленные экспорты и некоторые diagnostics endpoints требуют
  отдельного ревью scope, доступа и SQL-over-IO. Этот пакет их не исправляет.

Пункты 1–4 целиком пока не закрыты. Live нагрузка/провайдеры, production rollout
и восстановление новым финальным образом не проверялись этим прогоном.
