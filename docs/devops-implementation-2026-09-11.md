что старые production-контейнеры уже переведены на non-root.

## 2. Безопасная сборка и запуск API

- `.dockerignore` использует allowlist серверных каталогов и повторные запреты для секретов/дампов.
- `ops/package_backend.py` собирает только разрешённые tracked-файлы и явно перечисленные новые.
  `--revision` позволяет собрать исходный коммит для сравнения тестов. Артефакт не является backup.
- `requirements.lock` — зафиксированный snapshot версий production-зависимостей. Установка новой
  сборки прошла с `pip check`. Это constraints-файл, не hash-locked supply-chain attestations.
- Базовый Python 3.13 slim закреплён digest, версия релиза передаётся через `APP_RELEASE` и OCI label.
- `core/runtime.py` определяет роли `legacy`, `api`, `sync`, `scheduler`, `test` и строго проверяет
  значения флагов. По умолчанию остаётся `legacy`, чтобы не отключить существующие задачи случайно.
- При `api` не выполняются стартовый bootstrap схемы/SEO, embedded sync worker и API APScheduler.
  Ручная постановка SyncJob тоже не запускает встроенный worker в API-роли.
- `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `DB_POOL_TIMEOUT`, `DB_POOL_RECYCLE`, `DB_CONNECT_TIMEOUT`
  настраиваются. Для новых ролей defaults: 5 постоянных + 5 overflow, ожидание 5 секунд.
  Legacy defaults 20+30 сохранены. Бюджет считать по всем процессам, не по числу серверов.
- `/api/health/live` не обращается к БД. `/api/health/ready` проверяет соединение и точное совпадение
  `EXPECTED_SCHEMA_REVISION`, имеет локальные SQL timeouts, не раскрывает ошибки подключения.
  API-роль без ожидаемой ревизии возвращает 503. Миграций эти endpoints не выполняют.
- Логи можно направить в stdout (`LOG_TO_STDOUT=true`); файловый режим ограничен ротацией
  10 МиБ × 5 архивов для каждого из двух логов. Пути `LOG_DIR`/`REJECTED_LEADS_DIR` настраиваются.

**Важно:** нельзя сейчас просто поставить `APP_PROCESS_ROLE=api` в production: отдельные
entrypoints/доставка задач для sync и всех расписаний ещё не реализованы. Иначе часть фоновой
работы остановится. Роль — подготовленный механизм разделения, а не завершённая миграция.

Backend-артефакт больше не содержит дублирующую Vue-папку `/admirra`; официальный frontend
обслуживает её сам. Прямой вспомогательный URL `:8001/admirra/` в новом образе отсутствует.
До production-переключения проверить маршрутизацию nginx; frontend здесь не пересобирался.
Старые production-образы, содержащие `.env`/`.git`, пока не исправлены и не должны публиковаться.

## 3. Исправления очереди HTTP-запросов

В общей очереди limiter выбирался по типу worker, а не извлечённого задания: запрос VK мог
получить limiter Метрики, и наоборот. Теперь лимит зависит от `task.api_type`.

Время limiter переведено на monotonic clock. Shutdown сначала прекращает приём новых заданий,
даёт потребителям опустошить очередь, затем по ограниченному timeout отменяет зависшие работы
и ожидающие futures. Проверены отмена пользователя, зависший API, очередь ожидающих запросов
и остановка во время 429-backoff. Повторный start не создаёт дополнительные consumers.

Эти limiters пока общие **внутри процесса**, не между серверами. Это не распределённая очередь
и не замена Celery. При расширении необходимо вынести квоты в shared coordination, разделив
provider/credential/account scopes. Убийство потока legacy SyncJob этим изменением не исправляется.

## 4. Безопасность и оптимизация данных Метрики

Исправлен `_sync_metrika_goals_for_direct` (используется при sync Direct и привязанных целей Avito):

1. Сначала получить metadata и все статистические batches всех выбранных счётчиков.
2. Проверить структуру, даты, число метрик и значения; ошибка API не равна пустому периоду.
3. Суммировать счётчики в памяти в единственную строку `(integration, date, goal)`.
4. После успешного сбора заменить окно одним пакетом внутри SAVEPOINT, без commit внешней транзакции.

Раньше DELETE выполнялся до сетевых запросов, а ошибка batch превращалась в `[]`, после чего
сохранялись нули. Также при `autoflush=False` повторное добавление одной цели из нескольких
счётчиков могло создать дубли с последующим удалением одной из записей вместо суммирования.
Теперь провал сети, вставки или уведомления сохраняет старые данные, даже если вызывающая
функция ловит исключение и затем коммитит другой успешно загруженный канал.

Последние имена целей выбираются одним SQL с window function; наружу возвращается одна строка
на цель, а не вся история. Убраны SELECT для каждой записываемой строки. Тест на 60 строках
подтверждает один SELECT имён и пакетную запись, повтор того же окна не удваивает значения.
Это доказательство структуры запросов, **не замер ускорения production или нагрузочный benchmark**.

`get_goals_stats` больше не выдаёт пустую статистику на HTTP 400/401/403/5xx, некорректный 200
или усечённый ответ (`total_rows` больше полученных строк). Слишком сложный запрос по-прежнему
делится по датам; если API не может выполнить даже один день, ошибка остаётся ошибкой.
Пустой корректный 200 остаётся допустимыми нулями. Missing-goal уведомление учитывает наличие
цели на всех выбранных счётчиках, а не объявляет её пропавшей при отсутствии в одном из них.

Ограничения: внешний sync ещё может пометить частично обновлённую интеграцию общим SUCCESS;
нужны component watermarks/partial-status. Read-транзакция пока может оставаться открытой во время
HTTP. Другие пути синхронизации/атрибуции и межпроцессная защита ещё требуют переноса. Поэтому
дополнительные sync-workers в production пока запускать нельзя.

## 6. Последующие этапы и критерии допуска

1. **Backup/restore и сеть.** Получить независимое S3/backup-хранилище, проверить свежий dump +
   uploads + необходимые конфиги, выполнить restore drill. Для малого RPO — WAL archive, а не
   только ночной dump. Поднять private network/WireGuard, ограничить DB/Redis/firewall и проверить
   сохранность SSH-доступа. Не публиковать 5432/6379 на внешнем интерфейсе.
2. **Долговечные задания.** DB ledger остаётся источником правды; transactional outbox доставляет
   ID заданий в Celery. Выделить manual/nightly sync, reports, maintenance, AI/prewarm очереди;
   приоритет ручных с ограничением голодания ночных. Добавить heartbeat/lease/fencing, retry
   classification/backoff и атомарную дедупликацию. Проверить kill/restart, Redis outage и redelivery.
3. **Расписания и эффекты.** Один scheduler/beat, точно перенести 03:00 sync, 05:00 post-sync,
   минутные проектные отчёты, hourly VK maintenance, lead-validator и billing maintenance.
   Отправка отчётов имеет отдельные статусы получателей и uncertain outcome после сетевого timeout.
   Платежи не повторять автоматически без идемпотентности/сверки.
4. **Redis и SQL.** Broker/coordination (`noeviction`, persistence) отдельно от disposable cache
   (`allkeys-lfu`/TTL). Ключи кэша включают tenant и scope доступа, период, настройки, VAT,
   выбранные цели/кампании и data revision. Инвалидация после commit. Сначала убрать fan-out/N+1
   карточек и длинные SQL-транзакции, затем измерять p95/p99 и cache hit rate.
5. **API-2 и LB.** Вынести in-memory backfills/report tokens/artifacts/uploads, проверить AI SSE,
   graceful drain и открытые stream-соединения. Затем nginx upstream с одинаковым immutable
   release, readiness и корректным пулом; rolling deploy с возможностью отката к прежнему upstream.
6. **Приёмка.** Ночная и ручная синхронизация без двойного выполнения; точные сверки цифр/VAT;
   доставленные отчёты без необоснованных повторов; отказ Redis/worker/API, восстановление backup;
   проверенная tenant isolation, нагрузка и алерты по очередям, свежести данных, БД, диску и backup age.

Целевое начальное размещение: сервер 1 — PostgreSQL + edge/nginx + API; сервер 2 — workers +
раздельные Redis, затем API-2 при подтверждённом бюджете ресурсов. Не увеличивать concurrency
только потому, что появился новый сервер. PostgreSQL и edge пока остаются единичными точками
отказа: **два VPS не равны HA**. Managed HA/дополнительные узлы — следующий масштаб, с quorum/fencing.

## 7. Откат и недостающие внешние данные

На production в этом этапе откатывать нечего: ничего не переключалось, миграций БД нет.
Код foundation и исправление Метрики сохраняются раздельно, чтобы можно было отменить их независимо.
Локальные коммиты: `1285be6` — foundation; `e3c14a7` — Метрика. Push/deploy production не выполнен.
Стенд останавливается отдельной `compose ... down`; пользовательские файлы и production volumes не затрагиваются.

Перед настоящим deploy: записать image digests/compose revision, сделать свежую проверенную копию,
приостановить приём фоновых работ, дать текущим завершиться, выполнить совместимые миграции,
проверить новый release вне upstream, затем переключить роли/трафик. При сбое — старые образы
и upstream; не делать blind downgrade схемы или восстановление старого dump поверх новых платежей.

Нужны от владельца: независимое backup/S3-хранилище и его регион; возможности private network /
backup у провайдера; канал критических уведомлений. Секреты не присылать в открытый текст документа.
Пароли/ключи, ранее опубликованные в переписке, перевыпустить после настройки доступа по SSH-ключу.

## Источники решений

- Celery не обеспечивает exactly-once внешних эффектов; late acknowledgements требуют
  идемпотентности: [Celery tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html).
- Несколько процессов не должны делить APScheduler job store в текущей схеме:
  [APScheduler 3 FAQ](https://apscheduler.readthedocs.io/en/3.x/faq.html).
- Пулы считаются по процессам, соединения нельзя бесконтрольно наследовать после fork:
  [SQLAlchemy pooling](https://docs.sqlalchemy.org/en/20/core/pooling.html).
- Persistent broker и вытесняемый кэш имеют разные требования:
  [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/),
  [Redis eviction](https://redis.io/docs/latest/develop/reference/eviction/).
- Образы и сборка: [Docker secrets](https://docs.docker.com/build/building/secrets/),
  [установка Docker на Ubuntu](https://docs.docker.com/engine/install/ubuntu/).
- Пагинация/total_rows/20 метрик: [Yandex Metrica Reporting API](https://yandex.ru/dev/metrika/en/stat/openapi/data).
- Backup с возможностью PITR: [PostgreSQL 15 continuous archiving](https://www.postgresql.org/docs/15/continuous-archiving.html).
